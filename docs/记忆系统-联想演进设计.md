# Hebbian 联想记忆系统设计（§4.14 演进提案）

> 状态：设计草案，待评审。本文是对现行 §4.14「检索式记忆」的演进，不是推翻。
> 现状已落地的部分（两作用域 / L0L1L2 / 后台抽取 / 补抽游标 / `<memory-index>` 注入）全部保留，
> 本文只重做**注入侧**（从「模型自己 ReadMemory」改为「系统自动联想浮现」），并给抽取侧补上
> **深睡整合**与**关联网络**。

---

## 0. 一句话定位

让 Hebbian 名副其实：**记忆不是存下来再被检索的，是对话后异步「想」出来、并在下次对话中被自动「联想」唤起的。**
在线只读、离线只想；用得越多的记忆越容易被想起（fire together, wire together）。

灵感锚点：
- arXiv 2605.26099《Do Language Models Need Sleep?》——模型周期性「睡眠」，对累积 context 做 N 趟离线
  recurrent pass 固化进 fast weights，唤醒时只做低延迟读取，**把昂贵计算挪到睡眠时段，睡得越久收益越大**。
- 迁移到 agent 记忆：**浅睡增量抽取 + 深睡多趟整合**，深睡趟数 N 越多，关联网络越密、洞察越高层。

## 1. 现状盘点：已有什么、缺什么

| 能力 | 现状 | 本设计 |
|---|---|---|
| 离线形成记忆 | ✅ `RunFinished` 后便宜模型抽取，补抽游标，去重落盘 | 保留为**浅睡**，新增**深睡**整合 |
| 记忆分类 | ⚠️ 只有自由字符串 `category` | 收敛为 **kind 二分（stable / episode）+ 自由 tag**，不做领域硬类目 |
| 记忆间关联 | ❌ 无 | 新增 **Hebbian 关联网络**（带权重的边，激活共现 → 加权，长期不共现 → 衰减） |
| 注入 | ⚠️ 首条塞全量 L0 清单，**指望模型自己 ReadMemory** | 重做为**激活扩散**：每轮（可配）自动把相关记忆按强度分级浮现，模型零工具调用 |
| 强化 / 遗忘 | ❌ 无 | 被激活的记忆 importance↑、边权↑；冷记忆衰减沉底直到遗忘 |

**核心痛点**：现行注入是「把整本目录塞给你，自己翻」。本设计是「你提到 A，相关的 B、C 自动浮现在眼前」。

**为什么不做多类目**（评审收敛，2026-06-23）：探索阶段一度膨胀到六类（语义/情景/程序/地图/哲学/品味）。但多类目有三个根本毛病：① 分类是**作者视角**，而记忆好不好用取决于**读者视角**（下次什么场景需要它），不取决于它属于哪个学术类目；② 类目边界必然打架——「edits-worktree 让某模式失去意义所以删了」既是设计理性又是一次决策事件，硬三选一反而丢信息；③ 分类的真正目的是**服务检索**，而检索靠的是**关联边 + 语义相关性**，不靠类目树。结论：**少分类，重连接**——这恰是 Hebbian 名字的本意，价值在边不在节点标签。

## 2. 数据模型

### 2.0 定位：先做通用核心，领域能力靠抽取提示涌现

记忆系统的核心**必须领域无关**——同一套骨架既能记「用户爱喝美式、上周聊过的创业点子」，也能记「权限逻辑在 permissions/、某架构决策为什么这么定」。所以核心只保留三样普适的东西，**不把「项目地图/设计哲学」这类软件专属概念硬编码进存储**：

| 层 | 内容 | 领域相关性 |
|---|---|---|
| **通用核心** | kind 二分（stable/episode）+ scope + 自由 tag + 关联网络 | 领域无关，任何助手都用这套 |
| **领域适配** | 抽取 prompt 里的领域提示（「现在在聊代码项目，留意模块职责/设计决策」） | 在**抽取器**，不在**存储分类** |

这样「项目地图、设计哲学」不是新建的类目，而是通用骨架在软件领域**自然长出来的 tag + 关联簇**。换个领域（生活助手），同一套核心自动记别的主题，无需改存储模型。

### 2.1 分类模型：kind 二分 + scope + 自由 tag

复用现有 `storage::memory` 的 md + frontmatter，**只加字段，不改文件布局**：

```markdown
---
id: proj/architecture
scope: project            # 作用域：global | project（现状已有）
kind: stable              # 时效性二分：stable | episode（新增，替代原 type 多类）
tags: [architecture, rationale, constraint]   # 自由 tag，可多个（新增，替代硬类目）
summary: "..."            # L0
importance: 0.8           # 新增：激活强化 / 时间衰减后的当前重要度 [0,1]
last_active: 2026-06-22T..# 新增：上次被激活的时刻（遗忘判据）
updated_at: 2026-06-22T..
---
## 概览                    # L1
## 详情                    # L2
```

**三个正交维度，各管一件事**：

| 维度 | 取值 | 管什么 | 为什么够用 |
|---|---|---|---|
| **kind** 时效性 | `stable` / `episode` | 决定**要不要遗忘衰减** | semantic/episodic 的认知二分对任何领域成立（「巴黎是法国首都」vs「上周去了巴黎」）。这一刀几乎不会归错 |
| **scope** 作用域 | `global` / `project` | 决定**注入哪些 + 落盘到哪** | 现状已有，不动 |
| **tags** 主题 | 自由列表 | 服务**检索与聚类**，不做硬桶 | 一条可多 tag——「记忆绝不进 system prompt」可同时是 `rationale`+`constraint`，不必三选一 |

- **stable**：跨会话稳定的事实——X 在哪、为什么这么设计、红线、用户长期偏好。这是注入主力。
- **episode**：发生过的具体事件，带时间戳——「2026-06 修好了 partial sidecar，根因 BufWriter」。会过期、会衰减，但**联想价值最高**（用户再碰类似问题，自动想起上次怎么解的）。

> **为什么 kind 只二分不再细分**：stable 内部还能分「事实/理性/品味/术语/红线」，但那些**全部降级成 tag**。判一条记忆 stable 还是 episode 几乎无歧义（有没有「发生时间」）；而判它是 rationale 还是 constraint 全是灰色地带——所以前者做硬维度，后者做软 tag。**不好界定的情况自然消失**：因为允许多 tag 并存。

### 2.2 关联网络（新增 `links.jsonl`）

每个作用域 memory 目录下新增一个**只增式** `links.jsonl`，深睡时重算权重：

```
~/.hebbian/projects/<enc>/memory/
  architecture.md
  partial-sidecar-fix.md
  links.jsonl          ← {"from":"proj/architecture","to":"proj/partial-sidecar-fix","weight":0.6,"updated_at":"..."}
```

- **边 = 两条记忆的关联强度**，`weight ∈ [0,1]`。
- **赫布学习规则**：
  - 两条记忆在**同一对话**里被一起激活（共现）→ `weight += α`（fire together, wire together）。
  - 长期不共现 → 深睡时 `weight *= decay`，归零的边删除。
- **关联取代类目做聚类**：tag 相同 + 高频共现的记忆自然连成簇（如一堆 `architecture` tag 的记忆互相连成「项目地图簇」），**簇是涌现的，不是预先定义的桶**。
- **不上图数据库**：单机几百条记忆，邻接表（HashMap<id, Vec<(id, weight)>>）足够。深睡时整体重算并落盘。

> 决策：邻接表 over 图数据库。理由同 §13「砍向量库」——单机定位下，几百节点的邻接表内存常驻 + jsonl 落盘
> 远比引入图库轻。若未来记忆量级破万再议。

## 3. 什么时候提取：浅睡 / 深睡两段式

| 阶段 | 触发 | 干什么 | 成本 | 现状 |
|---|---|---|---|---|
| **浅睡 light** | 每个 `RunFinished`（现状触发点不变） | 增量抽本轮新事实 → 落盘为候选记忆。**只抽不整合** | 1 次便宜模型调用 | ✅ 已有，即现行 `extract_for_session` |
| **深睡 deep** | ① **session 空闲 ≥ T 分钟**（核心，见 §3.1）；② 浅睡累积 ≥ K 条新记忆；③ 显式触发（回填脚本 / 设置按钮） | 多趟反思：去重合并、tag 归一、**生成/重算关联边**、提炼高层洞察、importance 重算、过期遗忘 | N 趟，发生在用户不等待时 | ❌ 新增 |

### 3.1 空闲检测：run 完成后没人理，就睡（核心触发）

**和人一样——停下来不干活了，大脑才开始整理。** session 内部也需要睡眠：一个 Run 完成后，若过了 T 分钟还没有新用户输入，就触发深睡整理记忆。

```
RunFinished
   │
   ├─ 浅睡：立即抽本轮新事实（现状不变）
   │
   └─ 排一个 idle 哨兵：fire_at = now + T 分钟
         │
         ├─ T 分钟内来了新 user 输入 → 取消哨兵（用户还在，没睡）
         │     新 Run 结束后重新排（计时器重置）
         │
         └─ T 分钟到、期间无输入 → 触发深睡整合
               睡多深由「已空闲多久 + 累积多少新记忆」决定（见睡眠深度表）
```

**落点：复用现有 `WakeupScheduler`，零新基础设施**。它已是进程内独立线程的 1 秒 tick 调度（`scan_cron` 到点触发 `fire_at_ms`）。加一个 `IdleSentinel { session_id, fire_at_ms, last_msg_id }` + `scan_idle`（与 `scan_cron` 并列），`RunFinished` 时 `arm_idle(session_id, T)`，新 user 输入时 `cancel_idle(session_id)`。

**关键：计时器重置**。每次 `RunFinished` 都重排哨兵（取消旧的）——所以「连续干活」永远不会睡，只有真正停下来 T 分钟才睡。

**睡眠深度随空闲时长递增**（呼应论文「睡得越久越好」）：

| 空闲时长 | 类比 | 深睡趟数 | 干什么 |
|---|---|---|---|
| ≥ ~10min（T 默认） | 喝杯水 | 趟 1-2 | 去重整合 + tag 归一 |
| ≥ ~1h | 午饭 / 会议 | 趟 1-3 | 加联结建边 |
| 跨天（靠下次启动补判 `last_active`） | 下班睡一觉 | 全趟 | 加升华 + 遗忘衰减 |

**被新输入打断要安全**：深睡是纯派生任务（与浅睡同性质，不进 transcript / agent loop）。跑到一半用户回来 → 让当前趟跑完、落盘、退出，不阻塞新 Run；游标保证没整理完的下次接着整理。

**阈值定标有据**：本项目真实间隔分布——70.9% 的相邻消息间隔 < 5min（连续工作，绝不该睡）、20% 落在 5–30min、尾部才是 ≥1h。**T 默认 10min 能精准避开连续工作、只抓真正的停顿**。

> **与回填脚本统一**（§6）：实时运行用「idle 计时器等」，历史回填用「事后看两轮时间戳」——**判据完全相同**（空闲时长 → 睡眠深度），只是一个实时一个离线。同一个 `decide_sleep_depth(idle_minutes)` 两边复用，不写两套逻辑。


**深睡的 N 趟**（呼应论文「睡得越久越好」）：
1. 趟 1 — **整合**：把浅睡产生的零散候选去重、合并同义、消解冲突（新事实覆盖旧事实）。
2. 趟 2 — **tag 归一**：浅睡自由产 tag 会发散成近义词长尾。产一张同义合并表（`eval→evaluation`、`swebench-verified→swebench`），回写每条记忆的 tags。**只灭同义词拼写发散，不强压长尾**（见下方「长尾哲学」）。
3. 趟 3 — **联结**：扫描记忆两两关系，建立/更新 `links.jsonl` 的边权。
4. 趟 4 — **升华**：从一簇高频共现的记忆里提炼一条更高层的 `stable` 洞察（可选，趟数够才做）。
5. 趟 N — **遗忘**：importance × 时间衰减，低于阈值的冷记忆降级（先降 L2→L1，再 archive）。

趟数 N 可配；N=1 退化为「只整合」，N 越大网络越密。**昂贵计算全落在用户不等待的时段**——这是 sleep-time compute 的精髓。

> **长尾哲学（实测修正，2026-06-23）**：34 条记忆浅睡产 48 个 tag、30 个只出现 1 次。但「散」分两种——
> **同义词发散**（`eval`/`evaluation`，坏，趟 2 归一消灭）vs **长尾精确标签**（`macos`/`docker`/`field-naming`，
> 好，是特征不是噪声）。强行把 `macos` 并进 `pitfall` 反而丢掉「这是 macOS 特有」的关键信息。所以
> **不追求把 tag 数压到最小**（那是另一种过度设计）。低频 tag 不靠归并收敛，靠**关联网络兜底**：
> `r2e`/`docker`/`dataset` 三个单次 tag 不必合并成类目——它们所属的记忆在对话里共现，趟 3 会在三条记忆间
> 建边，检索点亮任一条、另两条沿边自动浮现，效果等同「一类」但无强行归类的损失。三机制分工：
> **kind 管时效 / tag 归一灭同义词 / 关联网络做涌现聚类**，各司其职，谁都不越界。

## 4. 怎么提取：kind 二分 + 自由 tag

浅睡的抽取 prompt 在现状基础上，让模型给每条候选记忆判**两样**：

1. **kind**（必填，二选一）：
   - `stable`：跨会话稳定的事实——X 在哪、为什么这么设计、红线、用户长期偏好。
   - `episode`：本轮发生的具体事件——修了什么 bug、做了什么决策、根因是什么（带时间，会衰减）。
2. **tags**（自由列表，0~N 个）：主题标签，模型自然产出（`architecture` / `rationale` / `preference` / `pitfall`…），**不给固定枚举**，避免逼模型往预设桶里塞。深睡时再对 tag 做一次归一（合并同义 tag）。

**领域提示**（领域适配层，不进存储）：抽取 prompt 里告诉模型当前语境——「这是一个代码项目，留意模块职责、设计决策、踩过的坑」。换成生活助手就换提示词，存储模型一字不改。

判定仍守现状红线：**不记 session 临时状态 / 调试中间结论 / 一次性数值**。
`episode` 的事件必须是「未来类似场景能复用」的，不是流水账。

## 5. 怎么注入：激活扩散（自动联想，本设计的心脏）

**彻底改变主路径**：不再「首条塞全量清单 + 模型自己 ReadMemory」，而是**每轮用户输入**系统自动跑四步，让记忆「浮现」到模型眼前，模型零工具调用。

```
用户输入一条 message
   │
   ├─ ① 种子激活（两阶段相关性，见 §5.1）
   │     当前 message → 命中 top-k 记忆作「种子」
   │
   ├─ ② 联想扩散（spreading activation）
   │     沿 links.jsonl 的边从种子扩散，activation(邻居) = activation(种子) × weight × 衰减
   │     提到 A，自动点亮常与 A 共现的 B、C —— 这就是「联想」
   │
   ├─ ③ 分级注入（按激活强度决定粒度，控 token）
   │     强  → 注入 L2 详情
   │     中  → 注入 L1 概览
   │     弱  → 只进 L0 清单（一行摘要）
   │     注入位置：当轮 user message 头部 SEMI 段（守 §0.9，不进 system、不破 cache）
   │
   └─ ④ 强化回写（赫布闭环）
         本轮被激活/被实际用到的记忆：importance↑、last_active=now、彼此 edge weight↑
         → 下次更容易被联想到；冷记忆自然沉底
```

`ReadMemory` 工具**保留为兜底**：模型想深挖某条弱激活记忆时仍可主动读，但不再是主路径。

### 5.1 种子激活的相关性：先符号后 LLM 两阶段（已选型）

```
阶段 1 — 符号粗筛（零依赖、零延迟、零成本）
   当前 message 的关键词 / 提到的文件名 / 符号名 / 报错串
   → 与每条记忆的 summary + category + body 做 BM25 / 子串命中打分
   → 取 top-N（N≈20）候选

阶段 2 — LLM 精排（便宜模型，仅在候选非空时一次调用）
   把 top-N 候选的 L0 清单 + 当前 message 一起喂便宜模型
   → 模型输出「真正相关的子集 + 每条相关度」
   → 作为种子激活强度
```

> 为什么两阶段：纯符号在代码场景命中率高（文件名/符号名/报错串都是强信号）但缺语义；纯 LLM 每轮一次调用
> 成本高且无相关性兜底。符号粗筛把候选压到 ~20 条再交给 LLM 精排，**既有语义又控成本**，且符号阶段
> 失败（无命中）时可直接跳过 LLM，零成本。
>
> 与 §13「砍向量库」不冲突：符号粗筛用 BM25/子串，不引入 embedding 依赖；语义靠便宜 LLM 精排补足，
> 复用现有 fallback 链模型。**这是「砍向量库」决策在联想场景下的自然延伸，需在 §13 追加一条说明。**

### 5.2 联想注入频率：做成开关（已选型）

设置「记忆」选项卡新增**联想注入模式**三档：

| 档位 | 行为 | 成本 | 适合 |
|---|---|---|---|
| `off` | 退化为现状：仅首条注入全量 L0 清单 | 最低 | 不想要联想 / 省钱 |
| `on_drift` | 检测到话题语义漂移才重新联想（默认推荐） | 折中 | 多数场景 |
| `every_turn` | 每轮都重算联想 | 最高 | 长对话、强上下文依赖 |

`on_drift` 的漂移检测：当轮 message 与上轮种子集的符号重合度低于阈值 → 判定漂移 → 重跑激活扩散；否则沿用上轮激活态（只做强化回写，不重算）。**用符号重合度做漂移判据，零额外 LLM 成本**。

## 6. 回填脚本：用历史对话跑一次全量记忆（你点名要的）

### 6.1 目标

项目已积累大量历史对话，跑一个一次性脚本，把它们「补做记忆」：按时间顺序重放每个 session 的对话，
浅睡逐轮抽取，**用对话之间的时间间隔判断是否触发深睡联想**。

### 6.2 时间间隔触发深睡（核心机制）

这是你的点子，落地为：**把历史对话的时间戳当作天然的「睡眠信号」**。**与实时 §3.1 共用同一个 `decide_sleep_depth(idle_minutes)`**——实时是 idle 计时器实测空闲时长，离线是两轮时间戳之差，喂进同一个函数得到同一套睡眠深度。

```
按 created_at 升序排列某项目的全部 (session, message) 事件流
逐轮（一个 user→assistant 往返）重放：
   │
   ├─ 每轮都跑浅睡抽取（增量抽事实，落候选记忆）
   │
   └─ Δt = 本轮结束 → 下一轮开始，喂 decide_sleep_depth(Δt)：
         Δt < T(默认10min)  → 同一工作时段，连续思考，不深睡
         Δt ≥ 10min         → 喝杯水级，轻整合（趟 1-2：去重 + tag 归一）
         Δt ≥ 1h            → 午饭/会议级，深整合（趟 1-3：加联结建边）
         Δt ≥ 跨天          → 睡了一觉级，完整深睡（全趟：加升华 + 遗忘）
```

> 为什么时间间隔是好信号：人脑的记忆固化正是发生在睡眠（尤其跨天的长间隔）。历史对话里两轮之间隔了
> 一夜，恰好对应「用户睡了一觉回来」——这正是该做深睡整合的时刻。**间隔越长，深睡趟数 N 越大**
> （分档映射），完美复刻论文「睡得越久收益越大」。

阈值（T / 1h / 跨天）做成参数，实时与回填共享同一组默认值。**实测背书**：本项目真实分布 70.9% 间隔 <5min（不睡）、20% 落 5-30min（轻整合）、尾部 ≥1h（深整合）——T=10min 精准避开连续工作。

### 6.3 脚本形态

新增 `heb` 子命令而非独立脚本（遵循「现有命令不够用时允许新增，但必须走 agent_core 主路径」）：

```bash
heb memory-backfill --workdir <项目目录> [--dry-run] [--deep-threshold 8h] [--max-passes 5]
```

- 走 agent_core 的 `memory_extract` + 新增 `deep_consolidate`，**不绕过任何主路径**（CLI 只是 surface 化）。
- `--dry-run`：只打印「会抽出哪些记忆 / 会在哪些轮触发深睡」，不落盘。
- 复用现有 fallback 链便宜模型；复用 `storage::memory` 落盘（文件锁）。
- 输出报告：处理了 N 个 session、M 轮对话、触发 D 次深睡、最终落盘 X 条记忆（按 type 分布）、建立 Y 条关联边。

### 6.4 幂等与安全

- 回填**复用现有去重逻辑**（同 slug upsert）：重复跑不会爆量，只会刷新。
- `--dry-run` 默认建议先跑一次看报告。
- 回填只读历史 session.jsonl + 只写 memory 目录，不碰 session 本身。
