## 0. 设计原则

以下 12 条为项目硬约束，任何修改不得违反：

1. **Surface 是壳**：Desktop 不实现业务，只翻译输入、渲染输出（CoreClient 接口同时也为远期 HttpCoreClient / 跨进程预留）
2. **Agent Core 是大脑**：agent_loop / 工具派发 / 上下文管理 / HITL / 观测 / 持久化全在这里
3. **双通路通信**：surface ↔ core 之间只走 **对话事件流** + **同步 API**
4. **配置同接口**：Desktop 通过 CoreClient 同步 API 访问 providers / sessions / settings；远期跨进程接 HttpCoreClient 复用同一 trait
5. **权限要持久化**：项目/全局审批写盘
6. **对话历史唯一文件**：每段对话 = 一个目录，目录内的 `session.jsonl` 是历史唯一文件，agent_core 落盘，Desktop 读它
7. **压缩信息不丢**：被压缩的原始内容存 txt/md 落盘，LLM 需要时按路径 read
8. **模型特性适配在 core 不在 gateway**：通用协议在 gateway，业务感知的特殊处理（DeepSeek thinking 拆解等）在 agent-core `model_adapters/`
9. **Mode 不进 system prompt**：切 mode 只动 SEMI 段 + 工具列表，**绝不动 STABLE 段**，保 prompt cache
10. **工具命名帕斯卡**：协议层 PascalCase（`Read` / `WebSearch` / `TodoWrite`），Rust 内部仍 snake_case
11. **MAX_STEPS = 100**（只计 ToolStep）：每个 Run 最多 100 次工具调用批次，达上限弹续跑审批
12. **文件并发安全**：所有共享文件（providers.json / permissions.json / session.jsonl）走文件锁 + atomic rename

## 3. 通信契约

### 3.1 通路 A：对话事件流（双向流式）

```
请求方向（surface → core）：Op
  StartRun                  起一次新 run
  InjectUserMessage         流式中插队
  ApprovePermission         回应审批
  AnswerQuestion            回答 agent 提问
  Interrupt                 中断
  Compact                   主动压缩
  Fork                      从某条消息分叉
  Rollback                  回到某条消息
  SwitchRunMode             切换运行模式（AskBeforeEdits / EditAutomatically / PlanMode / AutoMode）

事件方向（core → surface）：Event
  Run/Turn 边界：RunStarted / RunFinished / RunFailed / RunCancelled / TurnStarted / TurnFinished
  Run 挂起 / 唤醒（§4.12）：RunSuspended / RunResumed
  Step 边界：StepStarted / StepFinished（含 step_kind: Model | Tool）
  流式输出：TextDelta / TextDone / Reasoning
  工具：ToolCallDelta / ToolCallStarted / ToolCallFinished
  编辑快照（§4.13）：EditSnapshotCreated / EditReverted / EditRevertFailed
  HITL：PermissionRequested / PermissionResolved / UserQuestionRequested / UserQuestionAnswered / PermissionAutoJudged
  上下文：ContextCompacted / ToolResultsCompacted
  模式：RunModeChanged / PlanReady（PlanMode 完成时）
  钩子：HookFired
  杂项：Log / Error
```

## 4. Agent Core 详解

### 4.1 Session 与 Transcript

#### 4.1.1 Transcript 定义

```
transcript = 这段对话的所有消息按时间顺序排成的列表，结构是：

  Transcript:
    system: Option<String>                   可选的 system prompt
    entries: Vec<TranscriptEntry>

  TranscriptEntry:
    User      { msg_id, text, attachments[] }
    Assistant { msg_id, text, reasoning, tool_calls[] }
    ToolResult { call_id, outcome, content_or_ref }

每次调模型时，把 system + entries 拼起来全部发给模型。
模型按 OpenAI Chat / Anthropic Messages 标准 messages 数组解读。
```

#### 4.1.2 我们用扁平结构而非 codex 的 sub-item

调研发现 **codex 的 `ResponseItem` 是细粒度拆分**：

```
codex ResponseItem 是个大 enum，里面有 12+ variant：
  Message / Reasoning / LocalShellCall / FunctionCall / ToolSearchCall /
  FunctionCallOutput / CustomToolCall / CustomToolCallOutput / ToolSearchOutput / ...
```

每个 assistant 思考段、每个 tool_call、每个 tool_call_output 都是独立 item。

**好处**：fork 时能精确切到某个 tool_call 之前；序列化跟 OpenAI Responses API 一一对应；不同 provider 的特殊语义（如 LocalShellCall）能精确表达。

**坏处**：enum variant 多，维护成本高；每个 assistant 输出要拆 3-5 个 ResponseItem。

**本设计采用**扁平 3-variant（User / Assistant / ToolResult），不采用 codex 细粒度。理由：
- 当前用法（一个 Run 跑完后整体 commit assistant）扁平结构足够
- 多 provider 差异由 `model_adapters/` 处理，不污染协议层
- Fork / Rollback 以 msg_id 为切点足够精细，无需细到每个 tool_call
- 若未来需要细化（如单独存 reasoning entry），可向后兼容地扩 variant

#### 4.1.3 Session 是压缩策略的承载主体

压缩**不是**某个工具的责任，是 Session 在每轮模型调用前的自动行为。压缩策略组合配置在 Session 上：

```
SessionConfig.compaction:
  micro:
    enabled: true                       L0 微压缩
    trigger_threshold: 12               累计可压缩 tool result 数超此值触发
    keep_recent: 5                      保留最近 5 个不压缩
    tier_overrides: { ... }             用户可覆盖每个工具的 tier（§4.7）
  artifact:                              L1 大输出落盘
    enabled: true
    threshold_bytes: 16_384             > 16KB 落到 session/tool_results/<call_id>.txt
  structural:                            L2 结构化裁剪
    enabled: true
    token_budget_factor: 0.7            占 context_window 70% 触发
  llm_summary:                           L3 LLM 摘要
    auto: false                         false = 仅手动 /compact
    manual_to_md: true                  /compact 时把压缩前内容转 md 落盘
```

#### 4.1.4 Session API

```
Session::new(harness, config) → Session
Session::load(session_id) → Session              从 session.jsonl 重建
Session::append_user(text, attachments)
Session::run() / run_with_pending(...) → RunHandle
Session::compact(custom_instructions?) → Result   主动 L3
Session::fork(at_msg_id) → SessionId
Session::rollback(to_msg_id) → Result
Session::commit_assistant(text, ...) / .commit_tool_result(...)
Session::switch_run_mode(new_mode) → Result
Session::snapshot() → SessionSnapshot
```

**与参考项目对比**：
- claude-code-haha：Session 隐式，以 `agent task` 概念组织
- codex：显式 `Session` + `Turn`
- opencode：扁平 `Session`
- openhanako：`engine` + `session`
- 本设计层级最细（Session/Run/Turn/Step）。优势：事件粒度精确、metrics 维度清晰、支持流式插队等细粒度操作。劣势：概念抽象层数较 claude-code-haha 多，新人理解曲线较陡。

### 4.2 Run / Turn / Step：四级生命周期

#### 4.2.1 划分

```
Session  整段对话         transcript / workspace / definition / client 容器
 └── Run        一条 user message 跑到模型不再要求继续
      └── Turn       一次"用户输入 → 助手最终输出"的往返
           └── Step       一次原子动作
                          - ModelStep：一次 model.stream 调用
                          - ToolStep ：一批 tool_call 并发执行（同一批多个 tool call 算一个 ToolStep）
```

**Run 的三态**（§4.12 详）：`Active`（运行中）/ `Suspended`（task 退出 + 等 wakeup 的中间态）/ `Finished`（emit RunFinished）。Suspended 通过 RunCheckpoint 落盘，被 background-task 完成 / cron 触发 / 用户新消息 / 手动 abort 唤醒。

**新切分相对旧版的差异**：
- 旧版 Step = 模型调用 + tool_call 执行混在一起
- 新版 Step 拆开 → ModelStep 和 ToolStep 各自独立

#### 4.2.2 例子

**例 1：单轮带工具**
```
User: 帮我看 README.md
└── Run 2
    └── Turn 1
        ├── Step 1 (Model): "我先看一下" + ToolCalls([Read README])
        ├── Step 2 (Tool):  Read README → result
        │                   ← 插队检查点
        ├── Step 3 (Model): "这个文档讲了..." → Done
        └── 结束
```

**例 2：并发工具**
```
User: 把 src 和 tests 都过一遍
└── Run 3
    └── Turn 1
        ├── Step 1 (Model): "我并行扫描" + ToolCalls([Glob src/**, Glob tests/**])
        ├── Step 2 (Tool):  并发执行两个 Glob → 两份 result
        │                   ← 插队检查点
        ├── Step 3 (Model): "看到了，开始分析" + ToolCalls([Read X, Read Y, Read Z])
        ├── Step 4 (Tool):  并发执行三个 Read → 三份 result
        │                   ← 插队检查点
        ├── Step 5 (Model): "总结如下..." → Done
```

**例 3：流式插队（修正后的时机）**
```
User: 帮我重构这个文件
└── Run 4
    └── Turn 1
        ├── Step 1 (Model): 流式输出 → "我先读..." + ToolCalls([Read x.ts])
        │           ← 用户此时输入"用 hooks 重构"并 send
        │           ← runtime.inject_pending_input(text)
        │           ← ⚠️ 但 model step 还没结束（在流式 + ToolCalls 阶段）
        │             ⚠️ 不能这里 drain：模型刚返回 ToolCalls，必须先执行完
        ├── Step 2 (Tool):  Read x.ts → result
        │                   ← 插队检查点：drain pending → "用 hooks 重构" push 进 transcript
        ├── Step 3 (Model): 看到 Read 结果 + 新 user message "用 hooks 重构"
        │                   → 调整方向 → ToolCalls([Edit x.ts])
        ...
```

**插队规则（修正）**：

```
drain pending_inputs 的时机：
  ✗ 不能：ModelStep 进行中或刚结束（模型可能要求 tool_call，必须先跑）
  ✓ 正确：ToolStep 完成后（工具结果落地是安全点）
  ✓ 正确：Turn 边界（整轮干完）也是安全点
```

#### 4.2.3 两条队列：排队 vs 引导

surface 在 streaming 期间收到用户新消息，**默认不打扰本 Run**。两条队列各管一段：

```
1. next_run_queue（surface 持有，前端态）
   语义：等本 Run RunFinished 之后，作为新 Run 的 user message 顺次发出
   入队：用户在 streaming 中按 Enter / 点发送按钮
   消费：sendUserMessage 的 finally 钩子在 Run 结束时 drainNext()
         取队首作为下一次 sendUserMessage 调用
   不进 PendingInputs，不打断当前 Run

2. PendingInputs（agent-core 持有，本 Run 内）
   语义：当前 model_call + tool_call 完成后，作为 user message
        立即注入 transcript，让下一个 ModelStep 立刻看见
   入队：surface 显式调 inject_user_message —— 即"引导"语义
        触发方式：
          - streaming 中按 Shift+Enter（把当前 draft 推队首 + 立即引导）
          - 在 next_run_queue 列表上点 ↩「引导」按钮
   drain：agent_loop 在每次 ModelStep 之前 drain（§4.3.1）
   等价于：当前正在跑的 ModelStep/ToolStep 跑完，下个 ModelStep 立刻见
```

surface 列表上每条 queued 消息的三个图标（命名固定）：

```
↩  CornerDownLeft   tooltip "引导"
                    点击 = api.inject_user_message(...) → 走 PendingInputs
                    任意位置都可以点（不限队首）

🗑  Trash2          tooltip "删除"
                    从 next_run_queue 直接移除

✕  X               tooltip "放回输入框"
                    从 next_run_queue 移除 + 把 content/attachments
                    回写到 ChatInput 草稿（pendingDraft），让用户编辑
```

**为什么默认不"引导"**：用户体感上，发完话期望"轮到我"，而非"插到模型嘴里"。Shift+Enter（明确按下"立即"含义的修饰键）和 ↩ 按钮（明确点击）才是引导。

**为什么后端只有一条队列**：agent-core 不区分"排队 vs 引导"——任何到达 PendingInputs 的都是"已被 surface 决策为引导"。next_run_queue 是纯 surface 概念，后端不感知。

#### 4.2.4 MAX_STEPS = 100（只数 ToolStep）

```
理由：
  - 直觉上"100 轮"指工具调用轮次
  - ModelStep 是 ToolStep 的调度副产物，单独计数没意义
  - 防死循环主要看工具调用消耗资源
```

达上限：

```
emit ContinueLongRun { tool_step_count: 100, summary }
→ surface 弹审批：「这次 run 已经调了 100 次工具，继续 / 停止？」
  ✓ 继续 → tool_step_count 重置为 0
  ✗ 停止 → Run 正常结束（不算失败，emit RunFinished）
```

**与参考项目对比**：
- claude-code-haha：无 step 概念，按"agent loop iteration"计数
- codex：每个 Turn 内部循环计 iteration（model + tools 算一轮）
- opencode：同 codex
- 本设计的 ModelStep / ToolStep 分离粒度高于三家。优势：metrics 与事件粒度精确、插队检查点明确、续跑判定基于工具调用数而非混合迭代。劣势：协议层多一个枚举字段。

### 4.3 AgentLoop + Step Dispatcher

#### 4.3.1 逻辑骨架（伪代码）

```
async def agent_loop(ctx):
    while True:
        # 1. drain pending（只在 turn 开头 + tool_step 后；这里是 turn 开头）
        drain_pending_inputs_into_transcript()

        # 2. L0 微压缩
        report = microcompact(transcript)
        if report.changed: emit ToolResultsCompacted(report)

        # 3. hook: BeforeModelCall
        request = build_model_request(transcript, tools, run_mode)
        request = await hooks.fire("BeforeModelCall", request)

        # 4. ModelStep：调模型流式
        emit StepStarted(kind=Model)
        async for chunk in client.stream(request, cancel):
            emit_chunk(chunk)        # TextDelta / ToolCallDelta / Reasoning
        emit StepFinished(kind=Model)

        # 5. 看模型回什么
        match response:
            case Done:
                commit_assistant_message_to_jsonl()
                emit RunFinished(usage)
                break
            case ToolCalls(calls):
                commit_assistant_message_to_jsonl()
                # 进入 ToolStep
                emit StepStarted(kind=Tool)
                results = await dispatch_batch(calls)
                transcript.append_tool_results(results)
                emit StepFinished(kind=Tool)
                tool_step_count += 1

                # 6. 插队检查
                drain_pending_inputs_into_transcript()

        # 7. 达上限审批
        if tool_step_count >= MAX_STEPS:
            decision = await hitl.request_continue_long_run(tool_step_count)
            if decision == Stop:
                emit RunFinished(stopped_at_limit=True); break
            else:
                tool_step_count = 0

# 派发器
async def dispatch_batch(calls):
    tasks = [dispatch_one(call) for call in calls]
    return await asyncio.gather(*tasks)

async def dispatch_one(call):
    tool = registry.get(call.name)
    effects = analyze_effects(tool, call.input)        # §4.4.2

    # PlanMode 工具过滤（§4.4.3）
    if not is_tool_allowed_in_current_mode(call.name):
        emit ToolCallFinished(denied="tool not allowed in current mode")
        return ToolResult.denied(...)

    # 走 HITL Hub（审批是 HITL 的一种）
    decision = await hitl.check(tool.spec.name, effects, run_mode)
    match decision:
        case Allow: pass
        case Deny:  return ToolResult.denied(...)
        case NeedsApproval:
            emit PermissionRequested(...)
            decision = await hitl.wait(request_id)
            if decision == Deny: return ToolResult.denied(...)

    # 真正执行
    emit ToolCallStarted(call.id)
    raw = await tool.invoke(ctx, call.input)
    result = wrap_with_artifact_if_large(raw)        # §4.7 大输出落 txt
    emit ToolCallFinished(call.id, result)
    return result
```

#### 4.3.2 Rust 实现选择的权衡

Rust 与 Python / Go 在并发共享模型上有根本差异：每个值必须有明确所有者。同样的派发器逻辑：

- **Python**：`asyncio.gather(*[tool.invoke(...) for tool in tools])` 一行表达，并发错误延迟到运行时
- **Go**：N 个 goroutine + sync.WaitGroup，data race 须借助 race detector 才能发现
- **Rust**：`transcript` / `hitl` / `runtime` 等共享对象包装为 `Arc<Mutex<...>>`，并发 spawn 时 clone Arc；编译期强制处理所有权

**收益**：
- 数据竞争在编译期被消除（结构性杜绝"两个线程同时改 transcript"）
- 运行时性能优势（无 GC 暂停，Arc clone 是原子加 1）
- 类型系统可强制不变量（持可变引用时禁止 clone）

**代价**：
- 表达冗长（每个共享对象需要 `Arc::new` + `.clone()` + `.lock()`）
- 学习曲线陡（生命周期标注 `'a`、`Send + Sync` 等概念）
- 编译错误信息较长（一个所有权错误可能输出 20+ 行）

**本设计的折中策略**：
- 大部分共享对象（Harness / HitlHub / Workspace）使用 `Arc<...>`
- 独占对象（transcript 属于 Session）使用 `&mut self`
- 异步锁使用 `tokio::sync::Mutex`，避免阻塞 runtime

### 4.4 Tool 系统

#### 4.4.1 Tool 接口（极简）

只两个方法：

```
Tool 接口：
  spec() → ToolSpec { name, description, json_schema }
  invoke(ctx, input) → ToolResult
```

**不再要求 `classify` / `affected_paths`**——这俩职责挪到派发器外。

**为什么**：让工具自己描述「我是什么 + 我怎么干」就够了。权限和并发性**是上下文相关的**（同一个 `Bash "ls /tmp"` 和 `Bash "rm -rf /"` 风险天差地别），应该由派发器在拿到 input 后判断。

#### 4.4.2 权限审批与工具解耦（effects 分析）

派发器在工具旁边写一组 helper，**自己解析每次调用的 effects**：

```
analyze_effects(tool_name, input):
  Bash / PowerShell →
    segments = 段级判定（见下文 4.4.2.1）：
      把 `cmd1 && cmd2 | cmd3 ; cmd4` 按 `&&` `||` `;` `|` 拆成段
      每段独立产出：
        fingerprint    = 剥掉修饰符后的 "base sub"（"git push" / "rm" / "FOO=bar python"）
        write_targets  = 段内 `>` / `>>` / `tee FILE` / `sed -i FILE` / `cat > FILE` / heredoc / `python -c "open(...,'w')"` 的目标路径
        dangerous_kind = 命中的危险复合模式（见 4.4.2.2），None 表示安全
    paths            = ⋃ segments[i].write_targets ∪ [cwd]
    fingerprint(兼容)= segments[0].fingerprint   # 留给旧规则匹配点，过渡用
  Read / Edit →
    paths = [input.path]
  Glob →
    paths = [resolve_root(input.pattern)]
  Grep →
    paths = [input.path or workspace_root]
  WebSearch / Fetch →
    network = true
    domain  = parse_url(input.url).domain    # 用于按域名匹配规则
  Ask / TodoWrite / Skill →
    无外部 effects
```

派发器拿 effects 去查权限：

```
async def check_permission(tool_name, effects, run_mode):
    # 0. Bash/PowerShell 任一段命中危险复合模式 → 强制 NeedsApproval
    #    且禁止 AllowAndRemember 写盘（危险模式不可记忆）。规则匹配（1/2）
    #    不能把它洗白。
    if any(seg.dangerous_kind for seg in effects.segments):
        return NeedsApproval(kind=ToolCall, refuse_remember=True)

    # 1. Session 表 → Global 表：按段级 fingerprint 查
    #    Bash/PowerShell 要求所有段全 Allow 才整体 Allow；
    #    任一段命中 Deny → 整体 Deny；其余 → NeedsApproval。
    #    单段工具（Read/Edit/...）行为不变。
    decision = permission_store.find_segments(tool_name, effects)
    if decision: return decision

    # 2. 路径越界检查（含 effects.paths 中合并进来的 Bash 写文件目标）
    if any(p not in workspace.allowed_paths for p in effects.paths):
        return NeedsApproval(kind=PathAccess)

    # 3. 走 RunMode 判断（§4.4.3）
    return run_mode.judge(tool_name, effects)
```

##### 4.4.2.1 命令前缀剥离（fingerprint 语义）

Bash 段的 fingerprint **不是首个 token**，而是剥掉时间/优先级/调度修饰符与行内环境变量赋值后的 base command（可选子命令）。按顺序剥离：

```
1. timeout / time / nice / stdbuf / nohup / command / builtin / noglob
   （含其各自的子 flag，如 `timeout --kill-after=10s 30`）
2. 行内变量赋值：FOO=bar / FOO=bar BAR=baz （连续多个）
3. 取剩余首 token 作为 base
4. 取下一个非 flag 位置参数作为 sub（如 git status / npm install）
```

效果：

| 原始命令 | fingerprint |
|---|---|
| `timeout 30 git push origin main` | `git push` |
| `FOO=bar nice -n 10 cargo build` | `FOO=bar cargo build` |
| `RUST_LOG=info cargo run` | `RUST_LOG=info cargo run` |
| `LD_PRELOAD=/tmp/evil.so ls -la` | `LD_PRELOAD=/tmp/evil.so ls` |
| `nohup -- npm install` | `npm install` |
| `ls -la` | `ls` |

**关键点**：行内环境变量赋值**保留在 fingerprint 内**——避免攻击者用 `LD_PRELOAD=...` / `PYTHONPATH=...` 改变命令行为却复用 `python` / `ls` 等 allow 规则。代价：`RUST_LOG=info cargo run` 不会被 `Bash(cargo run)` 自动覆盖，用户可加 `Bash(RUST_LOG=info cargo run)` 或更宽的规则。这是 hebbian 不上 LLM classifier 的静态层做出的安全取舍。

##### 4.4.2.2 危险复合模式（强制审批 + 不可记忆）

下列模式被识别为高风险复合命令，**不管是否匹配 allow 规则，一律走 NeedsApproval，且 HITL 不把 AllowAndRemember 落盘**：

```
cd-git-compound         cd 后接 git（可执行目标目录的不可信 .git/hooks）
multi-cd                跨段多次 cd
write-git-meta          写入 .git/hooks/** / .git/config / HEAD / objects/** / refs/**
rm-rf-root              rm -rf 命中 / / ~ / $HOME / .. 等根级路径
ast-too-complex         含命令替换 / 进程替换 / 子 shell / 命令组 / 后台 `&` / 注释注入等无法精确解析的结构
```

这些模式与"剥离 + 段级 fingerprint" 是两套独立检查——前缀剥离让规则匹配正确，危险模式确保**即使**用户配过 `Bash(cd *)` allow，`cd /tmp && rm -rf foo` 仍然要审批。

#### 4.4.3 RunMode 四种（拍板版）

```
RunMode 枚举：

  AskBeforeEdits       【编辑前询问】
    UI 中文: "编辑前询问"
    行为: 命令（Bash/PowerShell）和编辑（Edit）都要审批
    目标: 新功能开发期间仔细把关

  EditAutomatically    【编辑自动执行】
    UI 中文: "编辑自动执行"
    行为: 编辑工具（Edit）自动放行；命令（Bash/PowerShell）仍要审批
    目标: 信任 agent 改文件，但命令保持警惕

  PlanMode             【计划模式】
    UI 中文: "计划模式"
    行为: Edit/Bash/PowerShell 从 ModelRequest.tools 删除
          只允许 Read/Grep/Glob/Fetch/WebSearch/Skill/Ask/TodoWrite
          额外注入 ExitPlanMode 工具
          agent 用 ExitPlanMode 退出（输出 plan markdown）
    目标: 探索 + 出方案再执行

  AutoMode             【自动模式】
    UI 中文: "自动模式"
    行为: 每个会改外界的工具调用前，调一次轻量模型判断 Allow / Deny / Ask
    限制: 仅 claude-opus-4-7 允许（保证判断质量）
    目标: 减少打断
```

**关键设计：mode 不进 system prompt**。切 mode 时：

- system prompt 字节恒定（保 prompt cache 命中）
- 只动两处：
  1. **SEMI 段**（首条 user message 头部 `<environment>` 块）写当前 mode 名 + 简短 hint
  2. **ModelRequest.tools** 列表过滤（PlanMode 时去掉 Edit/Bash/PowerShell）

切 mode 中途时，下一条 user message 头部会有 `<workspace-update>` 标注 mode 切换，让模型立刻知道。

**持久化**：`Session.run_mode` 字段（架构 §6.2 sessions storage）。切换走
`sessions::set_run_mode`——追加一行 `RolloutLine::MetaUpdate { run_mode: Some(_) }`，
不重写 messages；fold 按 last-wins 折叠到内存 Session。老 jsonl 无字段反序列化
默认 [`AskBeforeEdits`]，与切换前的硬编码行为兼容。Desktop chat 路径不再读 surface
in-memory state，每次 send_message 直接用 `prior_session.run_mode`。

#### 4.4.4 AutoMode 实现细节

```
async def judge_auto_mode(tool_name, input, effects, transcript_context, force_automode):
    if current_model not in AUTOMODE_ALLOWED_MODELS:   # ["claude-opus-4-7", "gpt-5.5"]
        return Ask("AutoMode 仅在 opus-4.7 / gpt-5.5 启用，当前 {model} 不支持自动判断")

    judge_prompt = build_judge_prompt(
        tool_name, input,
        effects=effects,                # 含 segments / write_targets / paths /
                                        #     dangerous_kinds (cd-git-compound 等)
        recent_transcript=transcript_context.tail(N=5),
    )

    judge_response = await judge_client.complete(
        request=ModelRequest(
            system=AUTOMODE_JUDGE_SYSTEM_PROMPT,   # 来自 prompts/automode_judge.md
            entries=[user(judge_prompt)],
            max_tokens=300,                        # ASK reason 要逐段解释，需更宽
            reasoning=Some(low),                   # 浅思考省 token
        )
    )

    decision = parse_judge_decision(judge_response)
    # force_automode 子开关：把 ASK 收紧为 Deny；不影响 Allow / Deny。
    # 适合"放手跑、不打断"场景——危险动作直接拒，不弹审批。
    if force_automode and decision is Ask:
        decision = Deny(reason="force-automode: ASK collapsed to DENY (" + decision.reason + ")")

    emit PermissionAutoJudged { decision, reason }
    return decision
```

**模型白名单**：`AUTOMODE_ALLOWED_MODELS = ["opus-4-7", "opus4.7", "gpt-5.5"]`，**exact match**——`claude-opus-4-7-20260416` / `gpt-5.5-preview` 这类带前缀或后缀的变体一律不命中，AutoMode 在它们上面静默降级 Ask。其他模型直接返回 `Ask` 不发请求（白名单内的模型都能稳定 follow 严格输出格式 + 段级 reason 推理）。后续如要扩白名单需在本节登记并补充评估理由。

**判官输入端**：除 `tool_name` / `input` / `recent_transcript`，必须把 [§4.4.2](#442-权限审批与工具解耦effects-分析) 的 `effects` 全量灌进 prompt——`segments[*].fingerprint` / `write_targets` / `paths` / `dangerous_kinds`。判官**不重复**解析 shell，只在 hebbian 静态分析结果上做最终拍板，所以 prompt 里需要明确告知它"hebbian 已识别到这些信号"。

**判官设计原则**（落在 [`crates/agent-core/prompts/automode_judge.md`](../crates/agent-core/prompts/automode_judge.md)，最终落地英文）：

1. **不可撤回/毁灭性命令分级**：CATASTROPHIC（跨工作区不可逆，如 `rm -rf /` / 改 `~/.ssh` / 写系统 launchd / `DROP DATABASE` / `kubectl delete ns prod` / `git push --force` 到 protected branch）/ DESTRUCTIVE（工作区内可逆但有副作用，如 `git reset --hard` / `git clean -fdx`）/ RISKY（网络外传敏感数据 / 改 `.env`/`secrets.*`）。**即使是 CATASTROPHIC，判官也不能直接 DENY**——用户可能就想跑这条命令（如运维场景）。判官应返回 ASK + 详细 reason，由用户最终拍板。
2. **ASK 时强制逐段拆解**：reason 字段必须按 `segments[*].fingerprint` 拆开，逐段说明该段会产生什么影响（如 `cd /etc && cat ~/.ssh/id_rsa && rm -rf x` 要明确告知"段 1 `cd /etc` 切到系统配置目录、段 2 `cat ~/.ssh/id_rsa` 会读取并显示 SSH 私钥、段 3 `rm -rf x` 会删除 `x`"）。让用户拿主意。
3. **DENY 仅用于**：hebbian 静态分析 `dangerous_kinds` 含 `ast-too-complex`（含命令替换 / 反引号 / process substitution，判官无法可靠分析）的 corner case，**且**判官也认为非用户意图——其它"危险"动作一律走 ASK。
4. **「鼓励语不解锁」原则**（[`Classifier B` line 172674](docs/权限沙箱-调研.md#293-四类用户自定义规则) 同款）：用户 / CLAUDE.md / 对话里的"放手做"/"我信任你"/"be autonomous" **不**降低判官门槛。authorization 只能来自 transcript 里**明确针对该次动作的意图陈述**（如"帮我清掉 build 目录"对应了具体的 `rm -rf ./build`）。
5. **工具切换绕过提示**（[`Classifier B` line 172683](docs/权限沙箱-调研.md#293-四类用户自定义规则) 同款）：判官需识别"用 Bash `cat >` / `sed -i` / `python -c "open(...,'w')"` / heredoc 改写 Edit deny 区文件"等行为视为绕过——hebbian 静态层已把 `write_targets` 合并到 `effects.paths` 让 FilePath deny 规则兜底，但语境推理（"agent 是不是在用 Bash 绕过 Edit 规则"）仍需判官最终把关。
6. **输出格式刚性**（fail-closed 配合 [`automode.rs::parse_decision`](../crates/agent-core/src/automode.rs) 兜底）：
   ```
   ALLOW
   DENY: <one short sentence>
   ASK: <segment-by-segment impact analysis>
   ```
   首行非这三档之一 → 兜底为 `Ask("判官返回未识别格式")`，绝不静默 Allow。

**`force_automode` 子开关**（Desktop 输入框命令 `//force-automode [on|off|toggle|status]`，无参数 = toggle；详见 §8 Desktop 命令系统）：

| 状态 | ALLOW | DENY | ASK |
|---|---|---|---|
| 默认（`false`） | 自动执行 | 自动拒绝 | 走 HITL 审批 |
| `force_automode=true` | 自动执行 | 自动拒绝 | **自动转 DENY**（在 `reason` 头部加 `force-automode:` 前缀）|

含义：用户在 Desktop 输入框敲 `//force-automode on` = "我要放手跑、不要打断我"。所有判官拿不准的动作直接拒，agent 自己换路子或汇报。与 [Classifier B 的 maxConsecutive / maxTotal](docs/权限沙箱-调研.md#296-连续--累计拒绝上限) 不同：hebbian 不做拒绝上限，留给上层 RunMode / 用户中断兜底。

**状态作用域**：`force_automode` 由 desktop 进程级 `ForceAutomodeState`（`Mutex<HashMap<session_id, bool>>`）持有，**不写盘**——重启 desktop 后回到 `false`。设计取舍：这是危险开关，重启回归默认比"用户上次启用后忘关"更安全；session.json 也因此保持向前兼容，老 session 反序列化无需迁移字段。

**`force_automode` 与 RunMode 正交**：它只在 `RunMode::AutoMode` 下生效，其他 mode 时这个 flag 被派发器忽略（避免在 `AskBeforeEdits` 模式里"force"绕过 HITL）。

#### 4.4.5 PlanMode 工作流

**进入**：
- 用户在 UI 下拉切到「计划模式」 → emit `RunModeChanged { from, to: PlanMode }`
- 派发器开始过滤 Edit/Bash/PowerShell

**探索期**：
- agent 用 Read/Grep/Glob/Fetch/WebSearch 调研
- 模型自己组织计划

**退出**：
- agent 调 `ExitPlanMode(plan_markdown)` 工具
- 该工具行为：
  1. 把 plan markdown 写到 `session/plans/plan-<ts>.md`
  2. emit `PlanReady { path, summary }` 事件
  3. 切换 RunMode 到 **之前的 mode**（PlanMode 进入前的那个），按以下规则：
     - **如果之前是 AutoMode**：UI 倒计时 10s，10s 内用户没干预则自动切回 AutoMode 真正执行
     - **其他模式**（AskBeforeEdits / EditAutomatically）：等用户手动按钮切回
  4. 返回 tool result "Plan recorded at {path}. Awaiting mode switch."

**ExitPlanMode 工具的特殊性**：
- 它只在 RunMode = PlanMode 时被注入 ModelRequest.tools
- 其他 mode 时模型看不到它

**plan 落盘位置**：
```
~/.hebbian/sessions/{session_id}/
├── session.jsonl
├── plans/
│   ├── plan-20260511-1430.md          ← 当前 plan
│   └── plan-20260511-1200.md          ← 历史 plan（用户切回 PlanMode 重新规划过）
└── ...
```

Bash 衍生（长跑命令周边，详见 §4.12）：
  BashOutput           查询后台 shell 的增量输出
  KillShell            强杀后台 shell

挂起 / 唤醒（详见 §4.12）：
  WaitForTask          挂起 Run 等指定 task_id 完成
  ScheduleWakeup       挂起 Run 等指定秒数后定时唤醒

**已删除**：TaskCreate/TaskGet/TaskList/TaskStop/TaskUpdate（不做 multi-agent）/ ImageGeneration / LSP / MCP（按需后期加）/ Write（与 Edit 合并：Edit 在 old_string="" 时承担创建语义；好处：diff 面板和 edits-worktree 快照只需要一种工具；代价：全量重写大文件时模型要 echo old_string，鼓励多次小 Edit 而不是大 Write）

#### 4.4.10 ReadState Tracker（Edit 前置 + stale check，对齐 Claude Code 2.1.144）

**为什么需要**：Edit 是写操作；如果模型没读过文件就盲改、或读过之后用户/linter 已经动过文件，盲写会丢用户改动。Claude Code 在 harness 层维护一份"已读文件状态表"，Edit 时强制检查。本节描述 hebbian 等价机制，行为完全对齐 Claude Code 2.1.144（实测：`tengu_edit_minimalanchor_jrn` flag 关闭路径）。

**数据结构**（Session 级，进程内）：

```rust
struct ReadState {
    content_hash: u64,           // 用 ahash / xxh3 算
    timestamp_ms: i64,           // 读取时拿到的 fs::metadata().modified()
    offset: Option<u64>,         // Read 工具的分页参数
    limit: Option<u64>,
    is_partial: bool,            // true = 仅读了部分页；Edit 仍要求 full Read
}

struct ReadStateTracker {
    states: Mutex<HashMap<PathBuf, ReadState>>,
}
```

挂在 `Session` 上（不进 jsonl；session reload 时清空——重新对话从零开始读）。

**Read 工具调用后**：用读到的内容算 hash + 当前 mtime 写入 tracker。

**Edit 工具调用前** 按以下顺序检查（**与 Claude Code errorCode 编号一致**）：

| 顺序 | 检查 | errorCode | 错误信息（中文） |
|---|---|---|---|
| 1 | path 在 workspace 允许范围 | 12 | 路径越界（由 dispatch 路径检查兜底） |
| 2 | `new_string` 字符合法（无 null 字节等） | 0 | new_string 含非法字符 |
| 3 | `old_string == new_string` | 1 | 没有变化：old_string 与 new_string 完全一致 |
| 4 | 不在 permission deny 目录 | 2 | 该文件位于权限拒绝目录 |
| 5 | 文件 ≤ 1GB | 10 | 文件过大（{size}），上限 1GB |
| 6 | 不是符号链接 / 特殊 mode | 11 | 不可编辑的文件类型 |
| 7 | 不是 `.ipynb` | 5 | Jupyter Notebook 请用 NotebookEdit（v1 未实现，给出提示） |
| 8 | **`old_string != ""` 时，文件必须已被 Read 过** | 6 | 文件尚未读取；先用 Read 工具读取后再编辑 |
| 9 | **mtime 与 readState.timestamp 比对**：当前 mtime ≤ 已读时戳 | 7 | 文件已被外部修改（用户 / linter / 其他工具）；请重新 Read |
| 10 | old_string 在文件中找得到（含 `\uXXXX` 容错） | 8 | 文件中找不到 old_string |
| 11 | old_string 唯一（除非 replace_all=true） | 9 | 匹配到 N 处，但 replace_all=false；请加更多上下文以唯一定位，或设 replace_all=true |

**第 10 步的 Unicode escape 容错**：当 old_string 含 `\uXXXX` 字面字符串、文件里却是真实字符（或反之），尝试两种规范化形式都失败才报错。错误信息追加 `(note: Edit also tried swapping \uXXXX escapes and their characters; neither form matched, so the mismatch is likely elsewhere in old_string. Re-read the file and copy the exact surrounding text.)`。

**第 10 步的 line ending 归一化**：匹配前把 file content 和 old_string 都做 `\r\n → \n` 归一化得到 `actualOldString`；实际 replace 用 actualOldString。这样 Windows 文件 / unix 文件不会因换行风格不匹配假报错。

**`old_string == ""` 特殊分支**：
- 文件不存在 → 视为创建新文件，写入 new_string；执行后更新 ReadStateTracker
- 文件存在但 `content.trim() != ""` → errorCode 3 "文件已存在，无法创建"
- 文件存在但全空 → 视为合法创建（覆盖空文件）

**execute 阶段（通过所有 validation 之后）**：

```
acquire FileLock(file_path)                ← 与 §4.13 edits-worktree 复用同一把锁
re-read file，二次校验 mtime（防 validation 与 execute 之间被改）
patch = compute_patch(content, actualOldString, new_string, replace_all)
edits_worktree.snapshot_before()           ← §4.13.2 拍 before
atomic_write(file_path, new_content)
edits_worktree.snapshot_after()            ← §4.13.2 拍 after
ReadStateTracker.update(file_path, new_content_hash, mtime_now)
emit ToolCallFinished + EditSnapshotCreated
release FileLock
trigger PostToolUse hook                   ← §4.8 既有
```

**与 Claude Code 的差异**：
- Claude Code 调 LSP `changeFile()` + `saveFile()` 通知 IDE；hebbian 没 LSP 集成，跳过
- Claude Code 有 `memoryWriteQueue` 给"修改是写 memory 文件"的场景排队；hebbian 暂不做 memory 系统，跳过
- Claude Code 有 `tengu_edit_minimalanchor_jrn` GrowthBook flag 切换两套 prompt（minimal anchor vs more context）；hebbian 不做 A/B，直接用 "more context" 那套（更稳）

### 4.5 HITL Hub

#### 4.5.1 三种 HITL 共用一张表

```
HITL 需求：
  Approval     destructive 工具调用要审批
  Question     ask 工具：agent 主动问用户
  PathAccess   工具想动 allowed_paths 之外的路径

存储：
  HitlGate.pending: { request_id → PendingHitl }
```

#### 4.5.2 HitlGate 与 HitlState 命名说明

`HitlGate` 与 `HitlState` 命名相似但职责完全不同，本设计保留现有命名：

```
HitlGate（在 agent-core 里，每段 run 一个）：
  作用：HITL 的核心逻辑表
  内部存：{ request_id → 等待这个回应的回信地址 }
  典型流程：
    模型说"我要审批" → HitlGate.open_approval(...) 给个 request_id + 把回信地址塞进表
    HitlGate 发事件 PermissionRequested 给外面
    在回信地址上挂起等
    用户回话了 → HitlGate.resolve(...) → 通过回信地址唤醒等待者

HitlState（在 apps/desktop 里，全局一个）：
  作用：路由 / 状态管理
  存：哪个 request_id 属于哪段对话 / 哪个审批了哪个没审批
  前端按"批准"按钮 → HitlState 反查 request_id 属于哪个 run → 转给对应 HitlGate

两者一为核心逻辑、一为 surface 端状态路由，职责正交，保留现有命名。
```

#### 4.5.3 AllowScope 4 种

```
AllowScope 枚举（内部英文，UI 中文）：

  Once         UI: "仅运行一次"
               不存任何地方；这次允许，下次同样命令重新问

  Session      UI: "当前对话不再询问"
               写入该 session 的 session.jsonl 作为 PermissionRule 事件
               重开这段对话仍生效，但开新对话要重新审批

  Project      UI: "本项目不再询问"
               写入 ~/.hebbian/permissions.json，rule.workdir = 当前 session.workdir
               同一 workdir（含子目录）下任何对话都生效；其他项目不受影响

  Global       UI: "始终允许"
               写入 ~/.hebbian/permissions.json，rule.workdir = null
               任何对话、任何项目都生效
```

**为什么 Project 和 Global 同文件存储**：两者结构相同，只是匹配阶段过滤策略不同（按 `rule.workdir` 是否覆盖当前 workdir）。同文件减少一份文件锁与一份热加载逻辑；旧版只有 Global 的规则缺省 `workdir = null`，向前兼容无需迁移。

#### 4.5.4 PermissionRule 数据结构

```
PermissionRule:
  id: uuid
  scope: Session | Project | Global
  tool_name: string                       "Bash" / "Edit" / ...
  workdir: Option<PathBuf>                Project 规则填 session.workdir；其他 = null
  matcher: 一个 enum，按工具语义选：
    Bash:           { commandPrefix: "git" }
    BashWithPath:   { commandPrefix: "rm", pathPrefix: "~/tmp" }
    FilePath:       { pathPrefix: "~/proj/" }
    Network:        { domainSuffix: ".example.com" }
    Any:            { /* 工具级，全放行 */ }
  decision: Allow | Deny
  createdAt: timestamp
  createdBy: "user" | "automode"
```

**持久化规则存储**：`~/.hebbian/permissions.json`（Project + Global 共用同一文件）

```json
{
  "rules": [
    { "id": "...", "scope": "Global",  "toolName": "Bash", "matcher": {"type":"Bash","commandPrefix":"git"}, "decision": "Allow", "workdir": null, ... },
    { "id": "...", "scope": "Project", "toolName": "Bash", "matcher": {"type":"Bash","commandPrefix":"cd"},  "decision": "Allow", "workdir": "/Users/x/proj/foo", ... },
    { "id": "...", "scope": "Global",  "toolName": "Read", "matcher": {"type":"FilePath","pathPrefix":"/etc/"}, "decision": "Deny", "workdir": null, ... }
  ]
}
```

**Session 规则存储**：写到 `session.jsonl`，作为一种 entry type：
```jsonl
{ "type": "PermissionRule", "rule": {...}, "timestamp": "..." }
```

### 4.6 PermissionStore

#### 4.6.1 接口

```
PermissionStore:
  match(session_id, workdir, tool_name, effects) → Option<Rule>
    匹配顺序 [Session, Project, Global]，命中即返回。
    - Session: 走 session_rules[session_id]（in-memory 视图）
    - Project: 走文件中 scope=Project 且 rule.workdir 覆盖当前 workdir 的规则
    - Global:  走文件中 scope=Global 的规则
    匹配前先调用 reload_if_stale 检查文件 mtime（见 §4.6.2）。

  add(rule) → Result
    Session → 仅写 in-memory session_rules（session.jsonl 落盘由 Recorder 负责）
    Project / Global → ~/.hebbian/permissions.json 重写（atomic rename），同步 in-memory cache

  remove(rule_id) → Result
  clear(scope) → Result
  list(scope) → Vec<Rule>
```

#### 4.6.2 加载与文件热加载

```
Session 启动:
  Project + Global 规则 → 一次性从 ~/.hebbian/permissions.json 加载到内存 cache，记下文件 mtime
  Session 规则 → 由 surface 在 load_session 时遍历 session.jsonl 中的 PermissionRule entry，
                   通过 store.load_session_rules(sid, rules) 灌入

热加载（每次 match 前）:
  stat ~/.hebbian/permissions.json：若 mtime > 上次加载值，重新读文件 + 替换 in-memory cache
  目的：用户手动改文件（添加 / 删除规则）下一次审批检查时立即生效，无需重启 Desktop

不会被 reload 清掉的：
  session_rules 是 in-memory map，不与 permissions.json 共用——热加载只动 Project/Global cache
```

**严禁**：在用户发新消息或 turn 切换时无脑调用 `store.load_session_rules(sid, vec![])` 重置 session 规则——这会把用户在前几轮选了 AllowAndRemember(Session) 的规则清空，导致审批反复弹出。

#### 4.6.3 文件锁

写 permissions.json 走 §6.3 的文件锁机制。Desktop 多窗口/多进程同时改不会互相覆盖。
热加载（读路径）走 `lock::read_locked` 即可，与写者天然互斥。

### 4.7 Context Engine 与压缩工件

#### 4.7.1 四层压缩

| 层 | 触发 | 干什么 | 工件 |
|---|---|---|---|
| L0 微压缩 | 每轮自动 | 压缩老工具结果（保留最近 K 个）| 原始内容存 txt |
| L1 大输出落盘 | 工具结果产生时 | > 6KB 落 txt，transcript 放占位符 + preview（Read 豁免——分页工具自身已做截断控制）| txt 文件 |
| L2 结构化裁剪 | budget 超阈值 | 保留 system + 最近 N 轮 | 无 |
| L3 LLM 摘要 | 用户 /compact | 调模型把整段历史浓缩 | 压缩前 transcript 转 md 落盘 |

**取消独立 BlobStore 抽象**——大输出和被压缩的小输出走同一套机制（落到 `tool_results/<call_id>.txt`），简化设计。

#### 4.7.2 L0 微压缩 Tier 化（默认配置）

按工具结果的"复看价值"分级：

```
Tier 1（一次过，最易压）:
  Bash / PowerShell      命令结果通常做完即过
  Grep / Glob            搜索结果，关心匹配项后就没用
  WebSearch              搜索结果摘要
  Fetch                  抓的页面（非长文）

Tier 2（中等，二次触发才压）:
  Read                   文件内容（用户可能还要追问）
  Edit                   改动 diff（用户可能想 review）

Tier 3（永不压）:
  Ask                    agent 提问的回答（重要决策证据）
  TodoWrite              状态型
  Skill                  指令注入
  ExitPlanMode           plan 内容
```

#### 4.7.3 微压缩算法

```
microcompact_step():
  candidates_tier1 = collect_tier(transcript, tier=1)
  candidates_tier2 = collect_tier(transcript, tier=2)

  total = len(candidates_tier1) + len(candidates_tier2)
  if total < trigger_threshold:        # 默认 12
    return None   # 不触发

  to_compact = []

  # 先压 Tier 1（除最近 K 个外）
  oldsters_t1 = candidates_tier1[:-keep_recent] if len(c1) > keep_recent else []
  to_compact.extend(oldsters_t1)

  # 还不够？再压 Tier 2
  if len(c1[-keep_recent:]) + len(c2) < keep_recent * 2:
    return commit(to_compact)
  oldsters_t2 = candidates_tier2[:-keep_recent] if len(c2) > keep_recent else []
  to_compact.extend(oldsters_t2)

  return commit(to_compact)

commit(items_to_shadow):
  for item in items_to_shadow:
    # 1. 原始内容已经在 session/tool_results/<call_id>.txt（L1 阶段就落盘了）
    # 2. transcript 里的 ToolResult.content 替换为占位符
    item.content = f"[此结果已被压缩。原始内容路径：{item.artifact_path}]"
    item.metadata.compacted = True
```

#### 4.7.4 LLM 按需检索的 prompt 设计

防止"压缩了又被白读"——三管齐下：

**1. Prompt 引导**（写在 `prompts/context_recall.md`，编译进二进制）：

```markdown
## 关于压缩占位符

当 transcript 里出现：

  [此结果已被压缩。原始内容路径：~/.hebbian/sessions/<sid>/tool_results/<call_id>.txt]

不要直接整文 Read 该路径。整文读会让压缩白做。

正确做法：

1. 优先用 transcript 现有信息
   - 「刚才看了哪个文件」→ transcript 中 ToolCall 参数已记录
   - 「之前的搜索结果是什么」→ 工具调用参数已记录 query / pattern

2. 用 Grep 在压缩 txt 文件内搜
   Grep("pattern", path="~/.hebbian/sessions/<sid>/tool_results/<call_id>.txt")

3. 用 Read 的 offset/limit 读关键区段（一般 ≤50 行）
   Read("...", offset=0, limit=50)

4. 整文 Read 仅在必要时（如复盘整段对话），且在 assistant 文本里向用户解释理由
```

**2. Read 工具默认安全行为**：

```
Read 工具行为（参 cc-haha）:
  - 默认 limit=100 行
  - 文件大于 2KB 且未传 limit → 返回前 100 行 + warning("文件较大共 N 行，建议指定 offset/limit 或先用 Grep")
  - 单行超 2000 字符 → 截断 + 警告
  - 必须显式 full=true 才整读
```

**3. 派发器层兜底**：

```
派发器发现 agent 对压缩 txt 文件触发 Read 整文（未传 limit 且未 full=true）:
  - 自动改成 limit=100
  - 返回结果 metadata.warning = "Read 自动限制为前 100 行，避免压缩失效"
  - emit Warning 事件给 surface
```

#### 4.7.5 L3 /compact 工件落盘

用户主动 `/compact "重构方案"` 时：

```
1. 转 markdown 落盘
   把当前 transcript 渲染成 markdown，存到
   ~/.hebbian/sessions/<sid>/compactions/compact-<yyyymmddHHmm>.md
   格式：
     # 对话压缩 - {timestamp}
     ## User
     ...
     ## Assistant
     ...
     ## Tool: Bash (call_id: ...)
     ...

2. 调模型生成摘要
   model.complete(系统 prompt = COMPACT_PROMPT, entries = transcript + 自定义指令)

3. 替换 transcript
   transcript = [
     UserEntry("[前情概要]\n{summary}\n\n如需详情，read ~/.hebbian/sessions/<sid>/compactions/compact-<ts>.md"),
     AssistantEntry("已收到前情概要，将基于此继续。"),
   ]

4. emit ContextCompacted { md_path, before_tokens, after_tokens, summary }
5. recorder 写 ContextCompacted entry 到 jsonl
```

#### 4.7.6 与参考项目对比

| 项 | claude-code-haha | codex | opencode | Hebbian |
|---|---|---|---|---|
| L0 微压缩 | ✓ 单一白名单 | ✗ | ✗ | ✓ Tier 化白名单（更精细）|
| L1 大输出 | snipCompact 中间裁剪 | 无 | 无 | 落盘 txt 文件（信息不丢）|
| L2 结构裁剪 | ✓ | ✓ | ✓ | ✓ |
| L3 LLM 摘要 | ✓ 4 段 prompt + auto / manual | ✓ inline + remote | ✓ 简单 | ✓ 沿用 claude-code-haha 多段 prompt |
| 压缩可追溯 | session memory | 无 | 无 | 落盘 md（LLM 可 read 回看）|
| 按需检索 prompt | 无 | 无 | 无 | 本设计独有（防止压缩被无效化）|

**Tier 化方案的权衡评估**：

**优势**：
- Read 类"上下文价值高"的结果被压缩的时机更晚
- Bash 类命令结果可优先压缩，节省更多 token
- 精度高于 claude-code-haha 的单一白名单

**劣势**：
- 每个工具需自报 tier，增加少量复杂度
- Tier 划分本身基于经验：例如 `bash "tree src/"` 输出可能比 `read mod.rs` 更有保留价值，按工具语义粗划分不一定最优
- 用户可能需要自定义 tier（已通过 `SessionConfig.compaction.tier_overrides` 提供配置接口）
- 真正最优策略需要 LLM 实时判断每条结果的重要性，但成本与 AutoMode 同等量级，不在本设计范围内

**选择 Tier 化而非 claude-code-haha 单一白名单的理由**：
- 实现复杂度增量极小（每个工具一个 tier 字段）
- 用户可感知精度提升（Read 内容更晚被压是可观察的）
- 通过 tier_overrides 提供配置回退路径

**已知边界情况**：用户跑高强度 Bash 工作流（如长时间 build / test）时，Tier 1 占大头可能导致有用的 build log 被过早压缩；此场景下可通过 tier_overrides 将 Bash 提升至 Tier 2。

### 4.8 Hooks 体系（参 CodeIsland 11 点位）

#### 4.8.1 Hook 点位

完整参 CodeIsland EventNormalizer 的归一化标准，跟主流 agent（Cursor / Gemini / Copilot CLI / TraeCli / Claude Code）互操作：

#### 4.9.3 流式输出处理（partial sidecar 方案）

**矛盾**：流式时频繁落 jsonl 会让文件膨胀（"h"、"he"、"hel" 全落）；但完全不落，中断时会丢中间输出。

**方案：partial sidecar**

```
agent_core 流式时：
  1. 每条 TextDelta / ToolCallDelta 写到 session/partial/<msg_id>.partial.jsonl
     （而不是 session.jsonl）
  2. emit Event::TextDelta / ToolCallDelta 给 surface（实时渲染）
  3. session.jsonl 暂时不动

stream 完成（Done）：
  4. 从 partial/<msg_id>.partial.jsonl 累积出完整 AssistantMessage
  5. 一次性 append AssistantMessage 到 session.jsonl
  6. 删除 partial/<msg_id>.partial.jsonl

中断（cancel / 进程崩溃）：
  partial/<msg_id>.partial.jsonl 还在
  下次启动时检测到 partial 文件 →
    把累积内容写成 AssistantMessage（标记 truncated=true 或 interrupted=true）追加 session.jsonl
    然后删除 partial 文件
```

**session.jsonl 的属性**：
- ✓ 只有完整 entry，**不存 delta**——体积可控
- ✓ append-only，reader 永远看到一致状态
- ✓ 中断恢复有 partial 兜底

**partial 文件的属性**：
- 临时性，正常完成后即删
- 写时高频但很小（每个 delta 一行）
- 文件锁锁的是 partial 自身，不锁主 jsonl

#### 4.9.4 Desktop 怎么读

```
两种读法：

1. 全量加载（恢复 / 列表展示）
   core_client.load_session(session_id) → Session
     → Recorder::read_full(jsonl_path) → 重建 Transcript + 元数据

2. 流式追溯（多窗口跟随同一 session）
   core_client.read_session_jsonl(session_id) → Stream<Event>
     → Recorder::tail(jsonl_path) → 类似 tail -f，inotify/kqueue 监听新行
```

Desktop 多窗口"实时跟随同一个正在跑的 session"也走 tail 路径。

#### 4.9.5 落盘策略明确化

```
落 session.jsonl 的 entry 类型：
  ✓ UserMessage                 用户输入完整
  ✓ AssistantMessage            助手完整一条（流式 Done 后一次写）
  ✓ ToolResult                  工具结果完整
  ✓ PermissionRule              审批规则
  ✓ Event（部分关键的）          RunStarted/Finished/Failed/Cancelled / ContextCompacted / ToolResultsCompacted / RunModeChanged / PermissionRequested / PermissionResolved
  ✓ Marker

不落 session.jsonl 的：
  ✗ TextDelta / ToolCallDelta / Reasoning chunks（走 partial sidecar）
  ✗ ToolCallStarted（仅渲染事件，没必要存）
  ✗ StepStarted/Finished（仅渲染事件）
```

| 项 | claude-code-haha | codex | opencode | Hebbian |
|---|---|---|---|---|
| 文件组织 | 单文件 + 散落配套 | 单文件 + sidecar | 单文件 | 目录化（一段对话一个目录）|
| Delta 落盘 | 不存 | 不存 | 不存 | partial sidecar（保中断恢复）|

### 4.11 Model Feature Adapter

#### 4.11.1 设计意图

模型协议层（model-gateway）应该 provider-neutral——处理 SSE 帧、OAuth、JSON schema 等通用问题。

但有些事是业务感知的，最典型：

- **DeepSeek thinking 拆解**：把 thinking 内容从 content 拆出来变两条流（Reasoning + Text）
- **Anthropic cache_control 自动插入**：在合适的 entry 上打 cache 标记
- **OpenAI Responses API 的 reasoning summary 透传**

这些**不能放 gateway**（业务感知太重），**也不放 agent_loop**（侵入主循环）。

#### 4.11.2 实现方式选择：装饰链 vs Hook

ModelFeatureAdapter 的实现存在两种可行路径：

**方案 A：装饰链（推荐）**

把 adapter 写成 `ModelClient` trait 的一个实现，包装在 chain 里：

```
Session.client = NamedModelClient(
                   ModelFeatureAdapter::DeepSeek(
                     InstrumentedClient(
                       DeepseekClient::new(...)
                     )
                   )
                 )
```

agent_loop 永远只调 `client.stream(...)`。请求和响应在装饰链里逐层穿过。adapter 改 stream_event 的逻辑写在它自己的 `stream` 方法里。

**方案 B：Hook 方式**

agent_loop 在收到每个 model stream event 后调 hook：

```
async for chunk in client.stream(...):
    chunk = await hooks.fire("OnModelStreamEvent", chunk)
    emit chunk
```

把 DeepSeek thinking 拆解写成一个 hook：注册 OnModelStreamEvent，invoke 里检查 event 来源然后改。

**对比**：

| 维度 | 装饰链 A | Hook B |
|---|---|---|
| 一致性 | ✓ 所有 client 都经同一链 | ✗ hook 调用点要 agent_loop 专门加 |
| 解耦 | ✓ adapter 跟具体 provider 自包含 | ✗ hook 全局共享，多个 hook 互相影响 |
| 性能 | ✓ 编译期决定 | ✗ 运行时遍历 hook 列表 |
| 可配置 | ✗ 用户改不了链 | ✓ 用户可加自己的 hook |
| 调试 | ✓ 链清晰 | ✗ 哪个 hook 改了 event 要追 |

**本设计采用方案 A（装饰链）**。Adapter 属于框架级特性适配，不应允许用户改写；用户可扩展性留给 Hook 体系（PreToolUse / PostToolUse）。

#### 4.11.3 落地

```
crates/agent-core/src/model_adapters/
├── mod.rs              注册 + 装饰链构造
├── deepseek.rs         拆 thinking
├── anthropic.rs        自动打 cache_control
├── openai.rs           （如有）
└── noop.rs             默认 passthrough
```

Session 构造时根据 `client.provider_kind()` 选 adapter 包一层；没匹配的用 noop。

### 4.12 长任务挂起 + Wakeup（设计）

**为什么需要这一节**：Bash 类长跑命令、定时回看任务进度、等待外部异步事件等场景，旧设计只能让模型轮询 `BashOutput`——既费 token 又卡 turn。本节集中描述「**挂起 → 后台事件 → 唤醒**」三阶段机制，目标是把"模型自己等"变成"被通知"。

#### 4.12.1 Run 的三态

```
Run::Active     正在跑（已有）
Run::Suspended  task 退出 + RunCheckpoint 落盘 + 等 wakeup（新）
Run::Finished   emit RunFinished，永久结束（已有）
```

Suspended 是中间态，会被以下任一事件唤醒：
- 关联的 background task 完成（exit / kill / fail）
- 关联的 cron 定时到点
- 用户在同一 session 发新消息（surface 触发）
- 用户手动 abort（→ Finished）

#### 4.12.2 整体数据流

```
模型调 WaitForTask / ScheduleWakeup
  ↓ 当前 ToolStep 跑完
agent_loop 检测 phase != Ready
  ↓
emit RunSuspended + 落 RunCheckpoint + 函数 return
  ↓ task 退出
[hebbian 进程仍在跑]

WakeupScheduler（进程内调度器、三个后台 task + 一个 mpsc）
  ┌── CronTimer 后台 task   每秒扫 cron 表 → WakeupEvent
  ├── BgFinishHook 后台 task  按 session_id 扫各 BackgroundShells → WakeupEvent
  └── WakeupDispatcher 消费者
        - 调用 ResumeHandler（App 层注册，desktop 路径 emit Tauri 事件
          `wakeup-fired`；frontend 收到后把 <wakeup> XML 作 user message
          发回后端；chat 命令检测到 RunCheckpoint 走 Session::resume_with）
```

**调度器是进程级单例**，但**它管理的 BackgroundShells 是 session-scoped**——
`register_session_shells(session_id, shells)` 按 sessionId 路由；
跨 session 互不可见（§4.12.2 修订决策）。

CronTimer / BgFinishHook 是进程内调度——hebbian 退出即丢，与"重启不自动 resume"决策一致（§13）。

#### 4.12.3 RunCheckpoint 持久化

落盘位置：`~/.hebbian/sessions/<sid>/run_checkpoint.json`（每个 session 至多一份）

```rust
struct RunCheckpoint {
    run_id, session_id, agent_def, run_mode, model_id,
    iteration: u32,
    model_step_index: u32,
    tool_step_index: u32,
    tool_call_dispatch_offset: usize,
    totals: TokenTotals,
    output_attachment_refs: Vec<PathBuf>,
    phase: RunPhase,
    suspended_at_ms: i64,
}

enum RunPhase {
    Ready,                                            // 准备进 next iteration（运行时态，不落盘）
    AwaitingBackgroundTask { task_id, max_wait_secs },
    AwaitingCron           { fire_at_ms, reason },
}
```

**transcript 不进 checkpoint**——agent_loop 唤醒时从 `session.jsonl` 重建，避免双源。

落盘时机：`emit RunSuspended` 之前 fsync。删除时机：唤醒成功 + 进入下个 iteration 顶端。

#### 4.12.4 两个新工具（命名 PascalCase，符合 §4.4.7）

```
WaitForTask
  params:  { task_id: string, max_wait_secs?: u32 }
  effect:  当前 ToolStep 完成后 → phase = AwaitingBackgroundTask
           注册到 BgFinishHook；max_wait_secs 给了再附加注册 CronTimer
  返回:    "已挂起等待 task=bash_001"
  class:   EffectClass::ReadOnly（不审批）

ScheduleWakeup
  params:  { delay_secs: u32, reason: string }  // delay_secs 上限 3600
  effect:  当前 ToolStep 完成后 → phase = AwaitingCron(now+delay)
           注册到 CronTimer
  返回:    "已设置 60s 后唤醒：check build progress"
  class:   EffectClass::ReadOnly（不审批）
```

v1 限制：`WaitForTask` 一次只等一个 task_id；模型可以串调多次。

#### 4.12.5 Wakeup 消息格式（XML 包裹 user message）

bg task 完成：

```xml
<wakeup kind="bg_task_finished" task_id="bash_001" exit_code="0" duration_ms="142000">
最后 4 KB 输出预览：
...
[完整输出：~/.hebbian/sessions/<sid>/bg/bash_001.log]
</wakeup>
```

cron 触发：

```xml
<wakeup kind="cron_fired" scheduled_for="2026-05-12T14:23:00Z" original_reason="check build progress">
60s 到了，按你之前 ScheduleWakeup 的设定唤醒。
</wakeup>
```

注入路径：作为 **user message** 加入 transcript（不是 system 也不是 tool_result），模型看到 `<wakeup>` 标签即知是系统通知。

#### 4.12.6 Wakeup 到达时的路由（关键）

WakeupDispatcher 根据 Run 当前状态分流：

| Run 当前状态 | 处理 |
|---|---|
| Suspended | 加载 checkpoint，inject `<wakeup>` 作为 user message，重 spawn |
| Active | inject `<wakeup>` 走 PendingInputs（§4.2.3 引导通路），下次 ModelStep 之前 drain |
| Finished | 仅写 session.jsonl 留痕，丢弃 |

→ 用户挂起后又发新消息触发 resume 的场景下，wakeup 到来时 Run 已经 Active，自动走"插队"语义，与 §4.2.3 现有机制对齐，**不需要新通路**。

#### 4.12.7 SEMI 段注入 `<background_tasks>`（§9.3 扩展）

每次发起 user message 时，若 BackgroundShells 当前有 `Running` 条目，在首条 user message 的 `<environment>` 块旁追加：

```xml
<background_tasks>
  - bash_001 running 142s `pnpm tauri dev`
  - bash_003 running 12s  `cargo test`
</background_tasks>
```

不动 system prompt（保 prompt cache，§0 / §9.3）。模型新发起 Run 时一眼看到当前后台情况。

#### 4.12.8 协议事件（§3.1 扩展）

```rust
EventPayload::RunSuspended {
    reason: SuspendReason,           // BackgroundTask | Cron | Manual
    resumes_at_ms: Option<i64>,      // cron 路径填
    waiting_for_task_ids: Vec<String>,
}
EventPayload::RunResumed {
    cause: ResumeCause,              // BgTaskFinished | CronFired | UserMessageArrived | ManualResume
}
```

`RunFinished` 仍只在 Run 进 Finished 态时发——Suspended → Resumed 不发 Finished。

#### 4.12.9 Surface 端 UX

- **不在挂起态弹文案**——挂起对用户而言是透明的"后台事件"，不打扰
- 右侧浮动栏（`FloatingTaskPanel` 旁，竖向并列）新增 **BackgroundTask 框**，展示：
  - 进程内 BackgroundShell 列表（task_id / 命令 / running 时长 / state）
  - cron 注册列表（still pending 的，距离唤醒时长 / reason）
  - 每条可点"强制结束"（bg）/ "提前唤醒"（cron）
- 挂起态下用户继续发消息：surface 仍走 sendMessage；后端 chat command 检测到 session 有 Suspended Run → 走 resume 路径，把消息作为 user message 接续到该 Run 的 transcript（**协议无新增**，纯后端路由）

### 4.13 Edit Tracker & Edits Worktree（设计）

**为什么需要这一节**：Edit 工具是不可逆的文件操作；agent 改了 N 次后用户想"只回退第 3 次"——既不能 reset 项目 git（用户自己的工作可能也在那），也不能整体 rollback session（其他改动还要保留）。本节描述一套**session 私有的 git worktree**（独立 .git，不挂在用户项目上），给 Edit 的每次调用都打快照，并允许**单次精确回退**。同时支撑前端三件事：流式 diff、审批前 diff、修改树侧卡。

**为什么叫 "edits-worktree" 而不是 "shadow-repo"**：与 git 的 worktree 概念语义对齐——一个独立可 checkout 的工作树用于追踪文件历史；同时与 Rust 模块 `crates/agent-core/src/edits/`、事件 `EditSnapshotCreated`、API `listEdits / revertEdit` 形成统一词族。注意它是一个**完全独立的 git 仓库**（自有 .git），不是 `git worktree add` 派生的 linked worktree——避免污染用户项目的 .git/worktrees。

#### 4.13.1 设计目标

1. **单次回退**：用户能在修改树里挑任意一条历史 edit 单独回退，不影响前后
2. **隔离**：影子仓在 `~/.hebbian/sessions/<sid>/edits-worktree/`，不污染用户项目 / .gitignore / git 历史
3. **并发安全**：多个会话同时改同一文件，按真实文件路径加锁串行（与 §0.12 / §6.3 一致）
4. **降级路径**：用户机器没装 git → 整套机制关闭，UI 提示"无 git，回退功能不可用"，但不阻塞 Edit 本身
5. **不动协议核心**：流式 diff 复用现有 `ToolCallDelta { arguments_delta }`，前端边收边解析 JSON 增量；新增的只有"快照创建/回退"3 个事件 + 4 个同步 API

#### 4.13.2 整体数据流

```
Edit 工具被 dispatcher 派发
  ↓ 在工具 execute() 前后包夹（不污染工具自身）
  ↓
acquire FileLock(real_file_path)        ← §6.3 同款 fd-lock
  ↓
edits_worktree.ensure_init()               ← 首次 lazy 创建
edits_worktree.materialize(real_path)      ← 真实文件 → 镜像到影子仓相同相对路径
edits_worktree.commit "before:<call_id>"   ← 拍下 before
  ↓
execute(tool)                           ← 真改用户项目里的文件
  ↓
edits_worktree.materialize(real_path)      ← 改后状态也镜像
edits_worktree.commit "after:<call_id>"    ← 拍下 after
metadata.append(EditEntry { call_id, before_sha, after_sha, real_path, action, ts })
emit EditSnapshotCreated
  ↓
release FileLock
```

回退路径：

```
revert_edit(snapshot_id):
  entry = metadata.find(snapshot_id)
  acquire FileLock(entry.real_path)
  # 反向 patch：把 after→before 这段差异 apply 到当前真实文件
  patch = edits_worktree.diff(entry.after_sha, entry.before_sha)
  apply_patch_atomically(entry.real_path, patch)
      ├ 成功 → edits_worktree.commit "revert:<call_id>" + emit EditReverted
      └ 冲突 → emit EditRevertFailed { error }；不强改用户文件
  release FileLock
```

**为什么用 reverse patch 而不是 `git checkout <before_sha> -- file`**：
用户可能在 agent 改完后又手动编辑了文件；直接 checkout 会盖掉用户手改。反向 patch 只回退该次 commit 的内容；冲突就拒绝，让用户自己合并。这与 §13 的"不替用户决策"原则一致。

#### 4.13.3 影子仓粒度

- **session 私有**：每个 session 一个 edits-worktree；不跨 session 共享（与 §4.12.2 BackgroundShells 决策一致）
- **lazy init**：第一次 Edit 才 `git init`；纯读会话永不创建
- **只跟踪改过的文件**：不预先 mirror 整个项目；用 `git add <file>` 按需加入索引
- **目录结构**：worktree 内文件用**真实文件相对于 workspace 根的路径**，例如真实文件 `/home/u/proj/src/a.rs`，workspace 根是 `/home/u/proj`，则 worktree 内是 `edits-worktree/src/a.rs`。Workspace 根之外的文件（编辑外部允许路径）用 `_external/<sha1(real_path)>/<basename>` 作为镜像位置，metadata 里记真实路径，UI 显示真实路径

#### 4.13.4 并发与锁

```
锁的 key  = 真实文件绝对路径
锁的实现  = 复用 storage::FileLock（fd-lock，§6.3）
锁的位置  = ~/.hebbian/sessions/<sid>/edits-worktree/.locks/<sha1(real_path)>.lock
锁的语义  = 同一文件互斥；不同文件不阻塞
```

跨会话同时改同一文件：先到先得，后到者阻塞到前者完成。

#### 4.13.5 metadata 文件格式

`~/.hebbian/sessions/<sid>/edits-worktree/.hebbian-edits.json`（追加式，atomic rename）：

```json
{
  "version": 1,
  "entries": [
    {
      "snapshot_id": "<short_uuid>",
      "call_id": "<tool_call_id>",
      "tool": "Edit",
      "real_path": "/abs/path/to/file",
      "action": "create" | "overwrite" | "modify",
      "before_sha": "<git_sha>",
      "after_sha": "<git_sha>",
      "before_bytes": 1234,
      "after_bytes": 1500,
      "ts_ms": 1747700000000,
      "reverted": false,
      "reverted_at_ms": null
    }
  ]
}
```

回退后**不删条目**，仅置 `reverted: true`（保留审计 + UI 灰显）。

#### 4.13.7 同步 API（§3.2 扩展）

```
listEdits(sessionId) → Vec<EditEntry>
diffEdit(sessionId, snapshotId) → DiffPayload {
    file_path,
    action,
    before_text: String,            // 完整修改前文本（create 时为空字符串）
    after_text:  String,            // 完整修改后文本
    before_sha,
    after_sha,
}
revertEdit(sessionId, snapshotId) → RevertResult {
    Success { restored_to_sha }
  | Conflict { reason }
  | NotFound
}
editsWorktreeStatus(sessionId) → EditsWorktreeStatus {
    enabled: bool,
    reason: Option<&str>,           // "no git binary detected"
}
```

**hunks 在前端算**：`DiffPayload` 不返回预切好的 hunks。前端 `<DiffViewer>` 用一次 LCS（按行）实时算对齐。理由：（1）省一份服务端 diff 库依赖（similar / imara-diff）；（2）streaming 态和 approval 态本来就拿不到服务端权威 hunks，三态统一走前端算更简单；（3）单文件 LCS 在 UI 端足够快。

#### 4.13.8 流式 diff（无新事件）

Edit/Write 的 arguments 在模型 streaming 阶段就开始通过现有 `ToolCallDelta { arguments_delta }` 流出。前端按工具名分流：

- 若 `name ∈ {Edit, Write}` → 进入"流式 diff"分支
- 维护 per-call_id 的 `partial_arguments_buf`（实际由 `StreamingAssistantPart.arguments` 累积）
- 用一个**容错 JSON 流式解析器**（只关心 `file_path` / `old_string` / `new_string` / `content` 字符串值），边收边把已确定的 string 片段拿出来渲染
- 渲染策略——**diff 的两端直接来自 args 本身，不读磁盘**：
  - `Edit`: before = `old_string` 已收部分，after = `new_string` 已收部分
  - `Write`: before = `""`（覆盖语义），after = `content` 已收部分
  - 已收的 after 末尾加光标占位，提示参数仍在写入
  - file_path 一旦闭合就显示在顶栏
- `ToolCallStarted` 到达 → arguments 完整、切换到"等待审批/执行"状态（DiffViewer 数据源不变，光标移除）
- `ToolCallFinished` + 匹配到 `EditEntry` → 切换到 "detail"，diff 改用 `diffEdit()` 拿到的服务端权威结果重渲（包含未改动的上下文行）

**为什么 streaming 态不读磁盘**：Edit 工具的语义就是"把 old_string 换成 new_string"，args 本身就是 diff 的两端；引入读磁盘 API 既要做路径校验又要异步等磁盘 IO，反而不如直接渲 args 直观，与"边写边渲"的视觉节奏更贴。代价：streaming 态展示的是**局部** diff（一个 hunk），不带前后文；切到 detail 态后会变成完整文件 diff——前者是"模型想做什么"，后者是"文件被改成什么样"，这是有意的语义切换。

**为什么不新增 `ToolPreviewDelta`**：会污染协议，且语义和 `ToolCallDelta` 完全重叠——后者本就是为流式参数设计。前端解析的代价（一个流式 JSON 解析器）比扩协议小。

#### 4.13.9 三种 UI 渲染态（前端职责）

`<DiffViewer>` 是三态共用的纯渲染组件，只接收 `beforeText / afterText / mode / streaming / expanded`；**布局（inline/split）与"是否放大"（expanded）是两个独立 state**——切换布局不会关掉放大框。数据源由调用方按下表选择：

| 态 | 触发条件 | 默认数据源（非放大） | 放大态数据源 |
|---|---|---|---|
| `streaming` | 工具 `status == "streaming"` 或 `running` 且尚无 EditEntry | `parsePartialEditArgs(arguments)` → before/after = old/new \| content | 同左（流式中没有完整文件可拉，放大仍是局部）|
| `approval` | `PermissionRequested { kind: ToolCall, tool_name ∈ {Edit, Write} }` | 同上，input 已是完整 JSON，走同一个解析器 | 同左（审批时尚未改文件）|
| `detail` | 工具完成 + `editSnapshots.find(call_id)` 命中 | **仍用 args 局部 diff**（与 streaming / approval 一致，零网络等待）| `diffEdit(sessionId, snapshotId)` 服务端权威完整 before/after，含未改动上下文行，类似 GitHub review |

**关键设计**：**非放大态永远不读 worktree**——只用 args 渲局部 diff，每次 ToolCallDelta 立刻刷新；避免工具完成瞬间画面"突然变全文"。**放大态才异步拉完整文件**——给用户看上下文的入口，类似 GitHub PR review。流式/审批态没有完整文件可拉，放大态也只是局部。

**GitHub 风格折叠**（detail 放大态独有）：拿到完整 before/after 后，`<DiffViewer>` 接收 `collapseContext={3}` 把视图按 hunk 折叠——任何 change 行（add/remove）及其周围 ±3 same 行直接展示；中间未被任何 change 邻居覆盖的纯 same 段折叠成一个跨双列的「展开 N 行原文（#start—#end）」按钮，点击展开成实际行。展开 state 在 DiffViewer 内部，切换 inline↔split 保留；流式/审批态不传 `collapseContext`，全展开。

`Esc` 在放大态退回非放大，不关掉父弹窗/卡片。审批批/拒后，approval 卡消失；同一个 call_id 在消息流里的 detail 卡承接。

**"chat 区域" 定义**：在 Desktop UI 中，"chat 区域" = ChatView 内 header（标题栏 + 模型/模式选择栏，`h-14 shrink-0`）下方、ChatInput（含 PermissionApprovalPopup 浮层）上方的消息列表区。Sidebar 不在 chat 区域内。

**放大预览 portal 锚点**：所有"放大查看"的模态（DiffViewer fullscreen / 工具卡片 ExpandButton / 后续任何 chat 内 modal）统一通过 `<FullscreenPortal>` 渲染到 `#chat-fullscreen-anchor`——它是 ChatView 中间消息列表外层 `relative` 容器内的 `pointer-events-none absolute inset-0` 锚点。放大内容用 `pointer-events-auto absolute inset-3` 撑满锚点 + 12px padding，再叠一层 `absolute inset-0 bg-foreground/30` 透明 backdrop 接收"点外面关闭"。这样确保：（1）只覆盖 chat 区域，不挡 sidebar / 标题栏 / 输入框；（2）多个 modal 共用同一坐标系，行为一致。

#### 4.13.10 修改树（输入框左侧悬浮卡）

数据源：`listEdits(currentSessionId)`，按时间倒序。空数组 → 整张卡片不渲染（不占输入框空间）。每条 entry 渲染：

- 文件名（hover 显示绝对路径，复用 §workspace 已有的 `PathHint` 组件）
- action 角标（创建 = old_string 为空 / 修改 = 有 old_string / 全量覆盖 = old_string 为整个旧内容）
- 时间（相对时间，hover 显示绝对）
- 操作：点条目 → 弹 DiffPanel detail；右键 → 回退；已回退态置灰

事件订阅：`EditSnapshotCreated` push 进树头；`EditReverted` 置灰；`EditRevertFailed` toast 提示。

#### 4.13.11 降级路径（无 git）

启动时（`Session::new` 或第一次写操作）调用 `which git`：

- **有 git**：正常启用 edits-worktree
- **无 git**：`edits-worktree` 不创建；`editsWorktreeStatus.enabled = false, reason = "未检测到 git，回退功能不可用"`；前端在输入框右侧渲染一条 toast warning（与 §4.12.9 BackgroundTask 浮动栏邻近的位置），不阻塞 Edit 本身执行

**为什么不降级到文件 .bak**：实现两套机制维护成本高；且 git 在 macOS/Linux/Windows 桌面环境默认装机率很高（用户基本都装了）。toast 提示比沉默兜底更诚实。

#### 4.13.12 体积与清理

edits-worktree 在长会话/大文件场景下会膨胀。策略：

- 单 session 内**不主动清理**（保证回退可用）
- session 关闭 + N 天后（默认 30 天，可配置 `settings.edits_worktree_ttl_days`）后台任务删整个 `edits-worktree/`；metadata.json 保留但所有 `reverted` 状态强制设为 true（UI 显示"已过期"）
- 删除 session 时（`deleteSession`）连带删 worktree

#### 4.13.13 与冲突场景

用户在 IDE 手改了文件 + agent 之后又改 + 用户想回退 agent 那次：

```
real_file 状态:  user_v1 → [agent commit A: a_v1] → user_v2 → revert(A)
```

reverse patch (a_v1 → user_v1) apply 到 user_v2：

- 若 user_v2 没动 agent 改的那几行 → patch 干净 apply → 真实文件回到 user_v2 的基础上去掉 agent 改动
- 若 user_v2 改了 agent 改的行 → patch conflict → emit `EditRevertFailed { error: "用户手改与回退冲突，请手动合并" }`，**不动文件**

这是有意为之的保守策略——比"猜用户意图"安全。

#### 4.13.14 Phase 落地

- **Phase A**（文档）：架构.md §3.1 / §3.2 / §6.1 / §13 / §4.13 更新；changelog 第 1 条
- **Phase B**（Edit 工具）：补齐 `tools/edit.rs`（架构.md §4.4.6 已声明但未实现），注册到 registry，单元测试

#### 5.2.1 DeepSeek 方言双协议路径

| 路径 | base_url 形态 | 入站协议 | thinking 字段形态 | reasoning 回传字段 |
|---|---|---|---|---|

公共规则（与 openhanako provider-compat/deepseek.js 一致）：
- `reasoning_effort` 命名空间只有 `high`/`max`；`Low/Medium/High → "high"`，`Extra → "max"`。
- thinking 启用时 `max_tokens ≥ 32768`，effort=high 抬到 65536，effort=max 抬到 131072。
- thinking 启用 + 历史里有 tool_calls/tool_use 的 assistant 消息：必须携带对应路径的 reasoning（`reasoning_content` 或 `thinking` block）；缺失则 fail-closed 抛 `ModelError::Other`，由 surface 提示用户「请压缩当前会话或开新会话」。
- OpenAI 兼容路径下 tool_calls 轮 `content` 不允许 `null`，缺时收紧成 `""`（v4 thinking + tool_replay 契约）。
- thinking disabled 时剥掉历史 messages 里的 `reasoning_content`，避免 server 拒绝。

实现位置：`crates/model-gateway/src/protocols/openai.rs::apply_deepseek_compat` 与 `protocols/anthropic.rs::build_body` 内的 `dialect_deepseek` 分支。这两段属于「业务感知的协议适配」，按 §4.11 应迁到 `agent-core/src/model_adapters/`（Step 12）；当前作为既有方言 hack 暂留 gateway 内，迁移时整体上移。

### 6.3 文件锁与原子写

#### 6.3.1 为什么需要

Desktop 多窗口/多进程真能同时跑，并发场景：
- 两个 Desktop 窗口同时改 providers.json → 后者覆盖前者
- 同时 append session.jsonl → 行错乱（POSIX 上 O_APPEND 单 syscall 原子但跨 4KB 不保证；Windows 不保证）
- 同时读写 permissions.json → 部分写

#### 6.3.2 实现

```
crates/agent-core/src/storage/lock.rs:

write_atomic(path, content):
  lockfile = path + ".lock"
  acquire_exclusive_lock(lockfile)    # 用 fs2 / fd-lock crate
  tmp = path + ".tmp.<random>"
  fs::write(tmp, content)
  fs::rename(tmp, path)                # atomic on POSIX；Windows MoveFileEx
  release_lock()

append_jsonl(path, line):
  lockfile = path + ".lock"
  acquire_exclusive_lock(lockfile)
  fs::open(path, O_APPEND | O_CREAT)
  write(line + "\n")
  fsync()
  release_lock()

read(path):
  # 用 shared lock，允许多读
  lockfile = path + ".lock"
  acquire_shared_lock(lockfile)
  content = fs::read(path)
  release_lock()
  return content
```

#### 6.3.3 粒度

```
每个文件一份独立 lock，不锁全局：
  ~/.hebbian/providers.json.lock
  ~/.hebbian/permissions.json.lock
  ~/.hebbian/sessions/<sid>/session.jsonl.lock
  ~/.hebbian/sessions/<sid>/partial/<msgid>.partial.jsonl.lock
```

不同 session 互不干扰；同 session 多写串行。

**与参考项目对比**：
- claude-code-haha：无文件锁（Node 单进程，多实例并发场景未处理）
- codex：atomic rename + fsync
- opencode：同 claude-code-haha
- 本设计采用更严格的并发保护：Desktop 多窗口/多进程可共享同一 data_dir，文件锁是最基本的安全保证

## 8. Desktop 命令系统（`//` 命令）

Desktop 输入框里以 `//` 开头的字符串被**前端拦截**，不发给 LLM——是 surface 层的本地控制命令。

### 8.1 设计原则

1. **`//` 前缀**：避免与 LLM 触发的"/"路径名、URL 路径、用户口语化的"/"碰撞（Claude Code 用单 `/`，hebbian 选双 `/` 区分）
2. **前端拦截**：用户按 Enter 时若 input 以 `//` 开头，frontend 解析命令名 + 参数，调对应 Tauri command，结果以 system notice 回显在对话流里——**不进 transcript / 不进 model request**
3. **每条命令独立**：一条 `//` 命令对应一组 Tauri command（`get_xxx` / `set_xxx`），后端落在合适层级——
   - 仅影响 desktop 进程行为（如 `force_automode` 子开关）→ 后端用进程级 state（`Mutex<HashMap<session_id, T>>`），重启回归默认
   - 会话级偏好需要跨重启保留（如 `RunMode`）→ 后端调 `sessions::set_xxx` append `MetaUpdate` 一行落盘，下次 `load` 时 fold 回内存
   - 影响 agent-core 内部状态（如未来 `clear_history`）→ 直接调 agent-core API
4. **失败 fail-closed**：未知命令 / 参数错误 → 前端弹 toast，**不**降级成普通 user message 发给 LLM（避免泄漏意图）
5. **本地派发，不写历史**：命令的结果以 toast 形式提示用户，**不**进 message 列表 / transcript / jsonl——避免污染 prompt cache 与 replay
6. **工具栏入口与命令并存**：每条命令也允许在工具栏挂一个图标按钮 / chip，点击后等价于在输入框敲对应 `//` 命令。键盘党用 `//xxx`，鼠标党点工具栏；二者共享 Tauri command，行为完全一致

### 8.2 命令清单（当前）

| 命令 | 参数 | 作用 | 后端 Tauri commands | 工具栏入口 |
|---|---|---|---|---|
| `//force-automode` | `[on\|off\|toggle\|status]`，空 = toggle | 切换 / 查询 [`force_automode`](#444-automode-实现细节) 子开关 | `get_force_automode(session_id)` / `set_force_automode(session_id, enabled)`（进程级 state） | `//` popup 列表 |
| `//run-mode`（暂未挂命令文字） | `<AskBeforeEdits\|EditAutomatically\|PlanMode\|AutoMode>` | 切换当前对话的 [`RunMode`](#443-runmode-工具集与策略) | `get_run_mode(session_id)` / `set_run_mode(session_id, mode)`（落到 `Session.run_mode`，跨重启保留） | mode chip 下拉 |

后续按需追加（如 `//clear` / `//compact <hint>`）。新增命令必须在本表登记并补充 Tauri command 签名。

### 8.3 失败模式

- **命令名拼写错误**（`//foce-automode`）→ 前端 toast "未知命令：foce-automode"，不发给 LLM
- **参数非法**（`//force-automode unknown`）→ 前端 toast "无法识别的参数：unknown（期望 on / off / toggle / status）"
- **当前没有打开的对话**（session_id 为空）→ 前端 toast "当前没有打开的对话"
- **Tauri command 失败**（agent-core 错误等）→ 前端 toast 显示后端错误文本
- **当前 RunMode 不是 AutoMode 时调 `//force-automode`** → 后端仍接受切换并写进程级 state；判官在派发器入口若发现 RunMode≠AutoMode 会自动忽略此开关，所以前端不需要加额外提示——切回 AutoMode 时这次设置会立刻生效

### 8.4 与参考项目对比

| 项 | claude-code | hebbian |
|---|---|---|
| 前缀 | 单 `/` | 双 `//` |
| 命令源 | 内置 + 用户 skill 注册 | 仅内置（当前阶段） |
| 路由层 | frontend → backend | frontend → Tauri command → agent-core setter |
| 输出 | 弹窗 + 行内 system notice | 行内 system notice + 失败 toast |

## 9. Prompt 体系

### 9.1 加载方式

本设计采用「单独目录 + md 文件 + 运行时加载」方案。

```
内置（编译进二进制兜底）:
  crates/agent-core/prompts/
  ├── base_system.md             STABLE：身份/安全/通用工具原则
  ├── tools_guide.md             STABLE：工具使用通用指南
  ├── context_recall.md          STABLE：压缩占位符按需检索指引（§4.7.4）
  ├── communication.md           STABLE：沟通风格
  ├── persona.md                 默认 persona（"你是 Hebbian agent..."）
  └── automode_judge.md          AutoMode judge 专用 prompt

用户自定义:
  ~/.hebbian/prompts/
  └── <agent_id>/
      └── persona.md              只能覆盖身份描述
```

**约束**：用户**只能覆盖 persona.md**。base_system / tools_guide / context_recall / communication 为内置不可改（改写将破坏 prompt cache 并影响系统稳定性）。

### 9.2 system prompt 组装

```
build_system_prompt(agent_id):
  # 都是从 include_str! 编译进二进制读
  base = load("base_system.md")
  tools = load("tools_guide.md")
  recall = load("context_recall.md")
  comm = load("communication.md")

  # persona 按优先级查
  persona = (
    load_user("~/.hebbian/prompts/{agent_id}/persona.md")
    or load_user("~/.hebbian/prompts/default/persona.md")
    or load("persona.md")  # 内置默认
  )

  return f"""
{base}

{tools}

{recall}

{comm}

{persona}
""".strip()
```

**这就是 system prompt 全部，跨 session 字节恒定**（除非用户改了自己的 persona），保 prompt cache 命中。

### 9.3 Mode 信息不进 system prompt

**约束**：mode 切换**绝不修改 system prompt**（否则破坏 prompt cache）。

```
mode 体现为两处：

1. ModelRequest.tools 列表过滤
   PlanMode: 去掉 Edit / Bash / PowerShell，加 ExitPlanMode
   其他 mode: 13 个工具全启用（按平台选 Bash 或 PowerShell）

2. 首条 user message 头部 <environment> 块（SEMI 段）
   <environment>
     cwd: /Users/me/proj
     allowedPaths: [...]
     platform: macOS 14.5
     shell: zsh
     date: 2026-05-11
     runMode: PlanMode
     runModeHint: "You are currently in Plan Mode. Use only Read/Grep/Glob/Fetch/WebSearch to investigate. At the end, call ExitPlanMode with a structured markdown plan."
   </environment>
```

切 mode 时不重发 system prompt；下条 user message 的头部加 `<workspace-update>` 块标 `runMode: <new_mode>` 让模型知道切了。

**`<background_tasks>` 块（§4.12.7）**：若 BackgroundShells 当前有 Running 条目，首条 user message 头部在 `<environment>` 旁追加。`<wakeup>` 块（§4.12.5）则是 Wakeup 路径注入的 user message 主体本身，不在 SEMI 段——它是一条独立的 user message。

### 9.4 模板变量渲染

只在 SEMI 段做（不在 system prompt 内）：

```
模板变量:
  {{cwd}}              当前工作目录
  {{allowedPaths}}      允许路径列表
  {{platform}}         macOS / Linux / Windows
  {{shell}}            zsh / bash / powershell
  {{date}}             YYYY-MM-DD
  {{runMode}}          AskBeforeEdits / EditAutomatically / PlanMode / AutoMode
  {{modelId}}          claude-opus-4-7
  {{enabledTools}}     启用工具列表（mode 过滤后的）
```

用 minijinja 或 handlebars 引擎渲染。

### 9.5 编译进二进制 vs 运行时读

- 内置 prompt 用 `include_str!`：编译进二进制
- 用户 persona 检测到才加载
- 改 persona 即时生效（不需要重启）

**好处**：发布版总有兜底，用户改坏 ~/.hebbian/prompts 不会让程序挂掉。

### 9.6 与参考项目对比

| 项 | claude-code-haha | codex | opencode | Hebbian |
|---|---|---|---|---|
| Prompt 形式 | TS 模板硬编码 | md + include_str!（每模型一份）| TS 模板 | md + include_str!（采用 codex 方案）|
| 模块化 | 部分 | 是 | 部分 | 是（6 个 segment）|
| 用户覆盖 | 无 | 无 | 有限 | persona 可覆盖（其他不可）|
| Mode 信息 | system prompt | system prompt | system prompt | SEMI 段（保 prompt cache）|

## 10. 数据流场景

### 10.1 用户发消息（核心循环）

```
[用户在 ChatInput 按 send "帮我看 README.md"]
   │
   ▼
api.send → core_client.submit(StartRun { input, ... })
   │
   ▼
actor.handle(StartRun) → session.append_user(...) → session.run() → RunHandle
spawn task: observer = DesktopObserver(app_handle)
            run.drive(observer).await
   │
   ▼ 后台 run task
agent_loop:
   emit RunStarted
   emit TurnStarted
   emit StepStarted(Model)
     model.stream → "我先看一下：" + ToolCalls([Read README])
   emit StepFinished(Model)
   commit AssistantMessage → session.jsonl

   emit StepStarted(Tool)
     dispatcher:
       analyze_effects(Read, {path: "README"}) → effects.paths=["README"]
       hitl.check(Read, effects, AskBeforeEdits) → Allow（Read 默认放行）
       emit ToolCallStarted
       result = await Read.invoke(...)
       wrap_with_artifact_if_large(result)   # > 16KB 落 txt
       emit ToolCallFinished
   emit StepFinished(Tool)
   commit ToolResult → session.jsonl

   drain pending_inputs

   emit StepStarted(Model)
     model.stream → "这个文件讲了..."
   emit StepFinished(Model)
   commit AssistantMessage → session.jsonl

   emit RunFinished { usage }
   │
   ▼ 同时 DesktopObserver.on_event
   翻译 → app_handle.emit("engine-event", ee)
   │
   ▼ 前端
store.applyEvent(ee) → ChatView 重渲染
```

### 10.2 切换 RunMode 不重建 system prompt

```
[用户在 Desktop 下拉切「计划模式」]
   ▼
client.submit(SwitchRunMode { from: AskBeforeEdits, to: PlanMode })
   ▼
session.switch_run_mode(PlanMode):
  1. 更新 session.run_mode 状态
  2. emit RunModeChanged
  3. recorder 写 RunModeChanged 到 session.jsonl
  4. 下一条 user message 自动注入 <workspace-update> 块带 runMode: PlanMode

下一次 model.request:
  - system prompt **字节不变**（保 cache）
  - tools 列表过滤：去掉 Edit/Bash，加 ExitPlanMode
  - 首条 user 头部 / 新 user 头部带 runMode hint
```

### 10.3 PlanMode 退出（AutoMode 倒计时）

```
[当前在 PlanMode（之前是 AutoMode 切过来的）]
[agent 调 ExitPlanMode(plan_markdown="...")]
   ▼
ExitPlanMode.invoke:
  1. 写 session/plans/plan-<ts>.md
  2. emit PlanReady { path, summary, previousMode: AutoMode, countdownSeconds: 10 }
  3. 切换 session.run_mode 回 AutoMode（待生效，倒计时中）
  4. 返回 tool result "Plan recorded. Switching back to AutoMode in 10s..."
   ▼
Desktop 弹窗:
  显示 plan markdown
  倒计时 10s 进度条
  [用户没干预] 10s 后自动 SwitchRunMode 真切到 AutoMode 继续执行
  [用户点"暂停"] 切到 AskBeforeEdits（不自动跑）
  [用户点"修改 plan"] 留在 PlanMode
```

如果之前是 AskBeforeEdits 或 EditAutomatically：

```
ExitPlanMode 写 plan + emit PlanReady { previousMode: ..., countdownSeconds: 0 }
留在 PlanMode，等用户手动切回
```

### 10.4 持久化审批的命中

```
[用户曾在某 session 选过 "AllowAndRemember { tool: Bash, pattern: 'git', scope: Session }"]
[已经写到该 session.jsonl 作为 PermissionRule entry]

[同 session 下次 agent 调 Bash "git diff"]
   ▼
analyze_effects → fingerprint="git"
hitl.check(Bash, effects, AskBeforeEdits):
   Session 表（启动时从 jsonl 加载的） → 命中 Bash + commandPrefix="git" → Allow
   → 不弹审批，直接执行
```

如果是 Global 规则：

```
[启动 session 时已经从 ~/.hebbian/permissions.json 加载 Global 规则到内存]
任意 session 下 agent 调 Bash "git diff" → Global 表命中 → Allow
```

### 10.5 微压缩 + LLM 按需 read

```
[累计 13 个 Bash/Read/Grep 调用]
   ▼
microcompact 触发：
  Tier 1 (Bash/Grep): 8 个老的压缩（保留最近 5 个）
  Tier 2 (Read/Edit): 暂不动
  每个被压缩的 ToolResult:
    - 原始 content 写到 session/tool_results/<call_id>.txt（其实 L1 阶段已写）
    - transcript 里 ToolResult.content 替换为占位符 + 路径

emit ToolResultsCompacted { count: 8, kept: 5 }
recorder 写到 session.jsonl
   ▼
模型新一轮调用时：
  发现 transcript 里某条 ToolResult 是占位符 + 提到 tool_results/abc123.txt
   ▼
模型按 context_recall.md 的指引：
  - 优先用 transcript 现有信息回答
  - 必要时调 Read 但带 limit
  → ToolCall: Read("...tool_results/abc123.txt", offset=0, limit=50)
   ▼
派发器：路径在 session 内部，自动放行；返回 50 行
```

### 10.6 流式中崩溃恢复

```
[agent 正在流式输出长 assistant 文本]
[流式中 partial/<msg_id>.partial.jsonl 已落了 100 条 TextDelta]
[突然崩溃]
   ▼
下次启动 hebbian:
  扫描 ~/.hebbian/sessions/*/partial/*.partial.jsonl
  发现 session-X/partial/msg-Y.partial.jsonl 还在
   ▼
  从 partial 累积出 text/reasoning/toolCalls
  写 AssistantMessage { text, reasoning, toolCalls, interrupted: true } 到 session.jsonl
  删除 partial 文件
  在 session 元数据标 "lastInterruptedAt"
   ▼
用户重开该 session 时：
  ChatView 渲染那条 assistant 消息时带 "已中断" 标记
```

## 12. 关键原则汇总

1. **Surface 是壳**：UI 代码不感知业务、不持有 transcript
2. **Core 是大脑**：所有业务逻辑、所有持久化决策在 core
3. **协议是合同**：surface ↔ core 之间只通过 Op + Event + CoreClient
4. **依赖单向**：surface → core → gateway / storage / observability
5. **持久化必经 Storage**：禁止 agent-core 直接 `fs::write`，必须通过 storage 模块
6. **模型特性适配位于 model_adapters/**：gateway 保持 provider-neutral
7. **HITL 必持久化**：AllowAndRemember(Session/Global) 必须落盘
8. **对话历史唯一文件**：一段对话 = 一个目录 + 一个 session.jsonl，Desktop 读它
9. **设置同接口**：Desktop 通过 CoreClient 同步 API 访问全局存储；远期 HttpCoreClient 复用同一 trait
10. **Mode 不修改 system prompt**：保 prompt cache，mode 通过 SEMI 段 + 工具过滤生效
11. **工具命名 PascalCase**：协议层使用 PascalCase，Rust 内部使用 snake_case
12. **文件并发安全**：所有共享文件必须经文件锁 + atomic rename
13. **所有调用真实模型**：单元测试需要可控行为时自行实现 ModelClient trait 作 test fixture，不在仓库公共代码暴露

| 4.5.3 | AllowScope 由 3 种扩为 4 种 | 新增 `Project`：rule.workdir = 当前 session.workdir，匹配时按 `current_workdir.starts_with(rule.workdir)` 命中。同 `~/.hebbian/permissions.json` 文件存储，仅靠 `scope` + `workdir` 字段区分 Global / Project。理由：之前"3 种 scope"决策诞生时认为 Session 就够覆盖"项目级"语义，但实际同一项目里开多个对话（线上多窗口、不同分支 worktree）的场景普遍——用户对一条 `cd` / `cargo` 规则希望"本项目内所有对话生效，但不要污染其他项目"。Global 太宽、Session 太窄、缺中间档 |
| 4.6.2 | PermissionStore 文件热加载 | match 前检查 `permissions.json` mtime，变化则 reload。理由：旧实现是进程级一次加载 cache，用户手动改文件需重启 Desktop 才能生效。代价：每次 match 多一次 stat 调用（同进程内仅 cache miss 时才真读文件），在权限决策路径上可接受 |
| 4.6.2 | Session 规则不允许在 turn 间被无脑清空 | 旧 desktop/chat.rs `store.load_session_rules(sid, Vec::new())` 在每次发消息时把累积的 session 规则覆盖为空——是真实 bug，已删除。`load_session_rules` 严格留给 surface 启动加载 session 时的"一次性灌入"路径 |

## 16. 参考项目综合对比

本章列出 Hebbian 设计与四个参考项目的逐项对比。标记 **本设计独有** 的项为 Hebbian 创新点；标记参考来源的项为采用其他项目方案。

### 16.1 架构分层

| 维度 | claude-code-haha | codex | opencode | openhanako | Hebbian |
|---|---|---|---|---|---|
| 顶层组织 | 单 `src/` 50+ 文件 | 20+ crate，按职责切分 | monorepo 17 packages | core + server + desktop + plugins | apps + crates 两层（≤6 crate）|
| Surface 数量 | 1（Electron）| 3（CLI / TUI / IDE）| 多（CLI / Desktop / Web / Slack / Console）| 2（CLI / Desktop） | 1（Desktop，Tauri）|
| Surface 接入方式 | bridge | app-server-client trait | sdk package | http server | CoreClient trait + Local / Http 实现 |
| 协议化程度 | 低 | 高 | 中 | 中 | 高（Op + Event + CoreClient）|
| Server 进程 | 内嵌 | 独立可选 | 独立可选 | 必备 | 暂不做，CoreClient 留接口 |

**评价**：codex 切割粒度过细（20+ crate 维护成本高），opencode 单 monorepo 17 packages 偏重，openhanako 必备 server 限制离线场景。本设计收敛为单 Desktop surface + ≤6 crate 轻量分层，CoreClient trait 抽象只为远期跨进程预留接口（不排期）。

### 16.2 会话与生命周期

| 维度 | claude-code-haha | codex | opencode | openhanako | Hebbian |
|---|---|---|---|---|---|
| Session 模型 | agent task（隐式）| Session + Turn | Session（扁平）| engine + session | Session + Run + Turn + Step |
| Step 粒度 | 无 | iteration（混合 model + tool）| 同 codex | 无 | ModelStep + ToolStep 分开 |
| 流式插队 | 不支持 | 不支持 | 不支持 | 不支持 | 支持（ToolStep 后 drain pending）|
| 并发工具调用 | 支持 | 支持 | 支持 | 支持 | 支持（ReadOnly 并发，其他串行）|
| Multi-agent | Task 工具 | agent_job / agent_tool | task.ts | subagent | 不做（D9）|

**评价**：本设计的 Step 粒度最细，是唯一支持流式插队的方案。本期不做 multi-agent，边界在 D9 决策中明确。

| Delta 落盘 | 不存 | 不存 | 不存 | partial sidecar（保中断恢复）|
| 流式中断恢复 | 重启重跑 | 从 jsonl 恢复（丢半轮）| 重跑 | partial 兜底保留半轮 |
| 数据目录跨平台 | platform-specific | ~/.codex | ~/.opencode | ~/.hebbian（跨平台一致）|
| 文件锁 | 无 | atomic rename + fsync | 无 | 文件锁 + atomic rename（每文件独立 lock）|
| 并发安全 | Node 单进程依赖 | 中等 | Node 单进程依赖 | 强（Desktop 多窗口/多进程并发场景）|

**评价**：本设计是四家中并发保护最严格的，原因是 Hebbian Desktop 允许同一数据目录被多个窗口/多个进程同时打开（用户可能同时跑多个 Desktop 实例对接同一对话历史）。

### 16.7 Prompt 体系

**评价**：本设计采用 codex 的 md + include_str! 方案，新增按 segment 切分与用户 persona 覆盖。Mode 信息位置（SEMI 段）是本设计独有，且是唯一保 prompt cache 的方案。

### 16.11 综合评估

**本设计相对参考项目的优势**：

1. 协议化程度最高（Op + Event + CoreClient 三合一）
2. 支持 Desktop 多窗口/多进程并发共享数据
3. 同时支持流式插队、AutoMode、压缩工件可追溯
4. 工具接口最薄，权限判断与工具解耦
5. Hook 体系与 CodeIsland 互操作，可复用其生态

**本设计相对参考项目的劣势与风险**：

1. Step 粒度细于其他三家，协议层概念较多，新人理解曲线较陡
2. partial sidecar 流式落盘机制需要额外维护中间状态文件
3. 压缩工件落盘机制增加磁盘占用，需配套 cleanup 策略
4. Tier 化微压缩对工具语义的依赖较强，部分场景可能误压
5. AutoMode 限定 opus-4-7 / opus4.7 / gpt-5.5 三个精确 id，model id 上游有任何后缀变体会让 AutoMode 静默降级 Ask
6. MCP / LSP 暂不接入，工具生态不如 codex / opencode 完整

**未采用的参考项目能力**：

- claude-code-haha 的 buddy / coordinator / daemon 等过度切分
- codex 的 cloud-tasks / collaboration-mode / experimental-api 等远期能力
- opencode 的 plugin / extension / enterprise 等企业向能力
- openhanako 的 plugin SDK 完整体系
