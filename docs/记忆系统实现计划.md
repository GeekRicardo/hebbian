# Hebbian 记忆系统实现计划

## Context（为什么做）

痛点：同一个项目每次新对话都要重新 explore 一遍目录结构 / 架构 / 命令。架构.md 第 1096 行当前白纸黑字写着「hebbian 暂不做 memory 系统，跳过」——本计划推翻它，落地一套**两作用域（global / project）记忆系统**。

设计参考 OpenViking，但按 hebbian 单机定位做了大幅裁剪：
- **砍向量库 / 砍 viking:// URI**（过度设计）。L0 初筛改成「注入清单让模型自己挑」，不用 embedding。
- **只有 global / project 两个作用域**（不要 session——session 本来就是自己的 context / jsonl 历史，不需要单独的会话记忆）。当前对话绑定了某 project → 写 project；否则写 global。
- 新增 OpenViking 没有的 **项目记忆**（探索项目时积累的结构/架构/约定/坑），解决「重复探索」。

保留 OpenViking 的精华：L0/L1/L2 分层思想（L0 注入初筛 → L1 概览 → L2 全文按需）、会话结束后台抽取闭环、失败补偿。

### 已确认决策（与用户对齐）
- 抽取时机：**每个 agent_loop（一个 turn）结束触发**，中间插队仍算一个 turn。
- 抽取范围：**项目 + 全局都自动写**。
- 抽取模型：设置里配**多个模型按序 fallback**，固定用便宜模型；每个模型最多重试 5 次再 fallback。
- 设置新增「记忆」选项卡：顶部从现有 provider 选模型，**每加一个实测连通**。
- 可靠性：后台记日志；某轮抽取失败 → 下次**把这轮一起补抽**（游标不前进）；失败弹**小 toast**。
- subagent **暂不注入记忆、也不给 ReadMemory/WriteMemory 工具**（先看主 agent 好不好用）。
- 设置「记忆」选项卡：顶部模型配置，下面展示**全局记忆列表**；当前对话绑定 project 时，再在下面展示**项目记忆列表**。
- 前端渲染：ReadMemory（读）/ WriteMemory（写）走**专门渲染**（非通用 tool 卡片）；每个 turn 抽取完后，在该 turn 末尾显示**一行小字**「本轮写入 N 条记忆 ▼」，点下箭头展开，**最多显示 5 条，多余在该小区域内滚动**。

### 硬约束（不可违反）
- **§0.9 prompt cache**：记忆**绝不能进 system prompt**。只进首条 user message 的 SEMI 段（`<memory-index>`）。
- agent-core 不能直接 `fs::write`，落盘必经 `storage::memory`。
- 工具名 PascalCase（§0.10）。
- 协议/事件只能 additive（加 variant，不改现有字段语义）。

## 二、落盘格式（storage::memory）

新建 `crates/agent-core/src/storage/memory.rs`，`storage/mod.rs` 加 `pub mod memory;`。
复用现有 `storage::lock`（原子写）+ `storage::projects::encode_workdir`（项目目录编码）。

```
~/.hebbian/memory/                        ← 全局记忆
  <category>/<slug>.md
~/.hebbian/projects/<enc>/memory/         ← 项目记忆
  structure.md / architecture.md / conventions.md / glossary.md / pitfalls.md / ...
  .memory_log.jsonl                       ← 后台抽取审计日志（只增）
```

**scope 只有 `Global | Project` 两值**。落盘**全程文件锁 + atomic rename**（`storage::lock`），抽取并发 / 主动 WriteMemory 同时写同一文件不丢更新。

每条记忆 = 一个 md 文件，frontmatter 携带 L0：

```markdown
---
id: proj/architecture
scope: project            # project | global
category: architecture
summary: "agent-core 是大脑，分层 DAG，改协议看 §3 通信契约"   # L0（注入用，≤120 字）
updated_at: 2026-05-29T...
---
## 概览                    # L1（长记忆才有；短记忆省略 → 三层退化成两层）
...
## 详情                    # L2（全文）
...
```

API（均走文件锁 + atomic rename）：
- `list_l0(scope, workdir) -> Vec<MemoryL0{id, summary}>`：扫 frontmatter 聚合 L0，给注入用。
- `read(id, level: Overview|Full) -> String`：Overview 只回「## 概览」段，Full 回全文。
- `write(scope, category, content, summary)`：upsert 一条记忆 + 回写 frontmatter；workdir→enc 定位项目目录。
- `append_log(workdir, entry)`：写 `.memory_log.jsonl`。

抽取游标（补抽机制）存进 session **meta.json**（复用 `storage::sessions_dir` 已管理的 meta）：
- `memory_cursor: Option<String>`（最后一次成功抽取覆盖到的 message id）。
- 抽取成功 → 推进游标；失败 → 不动游标，下次从同一游标起覆盖（自动补抽失败那段）。

## 三、两个工具：ReadMemory / WriteMemory

新建 `crates/agent-core/src/tools/read_memory.rs` 与 `write_memory.rs`，实现 `Tool` trait（参 `tools/read.rs` 模式），在 `tools/mod.rs::default_tools` 注册。

- **`ReadMemory(id, level?)`**：`level` = `"overview"`（L1）| `"full"`（L2，默认）。按 id 读记忆详情。description 保持简短稳定（**不内嵌清单**，避免动 tools 段击穿 cache）。
- **`WriteMemory(scope, category, content, summary)`**：模型主动记。`scope` = `project|global`。落盘必经 `storage::memory::write`（**不暴露内部路径给模型**）。当前对话**未绑定 project** 而 `scope=project` 时 → 降级写 global，结果文本说明降级原因。

**subagent 过滤**：在 `subagent/runner.rs::build_child_registry`（runner.rs:254）把 `ReadMemory`/`WriteMemory` 从子 registry 排除。

## 五、后台抽取（turn 结束触发 + fallback 链 + 补抽 + toast）

新建 `crates/agent-core/src/memory_extract.rs`。

**触发点**：每个 `TurnFinished`（agent_loop 一个 turn 结束）触发。spawn 一个**detached tokio 任务**做抽取，不阻塞 turn / 用户继续输入。每个 session 一把 `tokio::Mutex` 串行化，避免并发 + 与补抽竞争。

**抽取流程**：
1. 读 session transcript 中游标之后的 messages。
2. 用便宜模型 fallback 链跑抽取 prompt → 产候选记忆（项目类 + 全局类）。
3. 与现有 L0 去重 merge（prompt 内附现有 L0 清单，让模型输出 create/merge/skip 决策；参 OpenViking dedup）。
4. 写入 `storage::memory`（**scope 路由**：项目类 → 当前 project；无 project → 落 global；全局类/用户偏好 → global）+ `append_log`。
5. 成功 → 推进 meta.json 游标；失败 → 不动游标（下次 turn 自动把这段一起**补抽**）。

**fixed-model fallback 链**：从 `MemorySettings.models`（有序 `[(provider_id, model)]`）依次取；每个模型用 `ModelClient` 调用，**最多重试 5 次**仍失败 → 下一个；全链耗尽 → 整体失败。

**日志**：每次抽取 attempt（模型、重试次数、成功/失败、耗时）写 `.memory_log.jsonl` + `tracing`。

**事件（turn 归属，走 run 事件流）**——新增两个 additive `EventPayload` variant，都带 `turn_id`，前端按 turn 渲染：
- `MemoryExtracted { turn_id, written: Vec<MemoryWriteSummary{id, summary, scope, op}> }`：成功，驱动 turn 末尾的「写入 N 条记忆」摘要行。
- `MemoryExtractionFailed { turn_id, reason }`：失败，驱动 toast。

**run 关流前 drain**：抽取是 turn 后异步任务，最后一个 turn 的抽取可能晚于 `RunFinished`。harness 在关闭 run 事件 channel 前 **await 本 run 在途的记忆抽取任务**（上限受 5 次重试 fallback 超时约束），保证事件还能从 run 流发出、挂到对应 turn。

**翻译/映射**：`apps/desktop/src/chat.rs` 翻译两个新事件 → 前端 `types.ts` 映射；CLI 加 `DaemonEvent::MemoryExtracted` / `MemoryExtractionFailed`（旧脚本忽略未知 event，兼容）。
