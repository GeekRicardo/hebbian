前端状态机

useStore 里的 applyEventToSlot 是前端最核心的纯函数。它把每一个后端事件「折叠」进 slot 状态，驱动整个 UI 的变化。

🎯
比喻：就像快递分拣中心

后端往传送带上放包裹（事件），每个包裹上贴着标签（event.type）。分拣员（applyEventToSlot）看一眼标签，然后把它放到正确的架子上：TextDelta 放 streamingText 架子，ToolCallStarted 放 streamingParts 架子，TurnFinished 检查要不要冻结当前架子的内容……

SessionStream：每个 Run 的状态槽

每次 sendUserMessage 被调用，前端创建一个新的 SessionStream slot。它包含 Run 进行中的所有实时状态：

📝

streamingText

当前 Run 累积的所有文本。每次 TextDelta 就追加。Run 结束 reload 后，由 session.jsonl 接管。

🧩

streamingParts

结构化的输出段：文本、推理、工具调用卡片（按真实发生顺序穿插）。MessageBubble 直接吃这个结构渲染。

📋

liveTimeline

Run 内的时间线：冻结的 assistant 快照 + 用户插队消息。Run 结束清空，由 session.messages 接管渲染。

📍

assistantInsertPos

游标：当前 streaming 在 liveTimeline 里的插入位置。冻结后游标推进到末尾。

applyEventToSlot：事件分发核心

每个后端事件的 type 决定走哪个分支。这是纯函数——接收旧 slot + 事件，返回新 slot。

CODE — useStore.ts:341 

function applyEventToSlot(
  slot: SessionStream,
  e: EngineEvent
): SessionStream {
  if (e.type === "text_delta") {
    return { ...slot,
      streamingText: slot.streamingText + e.text,
      streamingParts: applyTextDelta(slot.streamingParts, e.text)
    };
  }
  if (e.type === "text_done") {
    const r = applyTextDone(
      slot.streamingText, slot.streamingParts, e.full_text);
    return { ...slot, ...r };
  }
  // ... tool_start, tool_done, turn_finished ...
}

核心的事件处理函数——纯函数，接收旧状态+事件，返回新状态

SessionStream：当前 Run 的所有实时状态

EngineEvent：后端发来的结构化事件

返回新的 SessionStream（不可变更新）

TextDone：用 applyTextDone 判定是否需要追加全文

参数：当前累积文本、当前 parts、后端给的 fullText

把 applyTextDone 的结果合并回 slot

还有 tool_start、tool_done、turn_finished 等十几种分支

applyTextDone：最容易出 Bug 的函数

这是前端流式累积的核心逻辑，也是上一轮 Bug 修复的关键。

CODE — streamingParts.ts:66 

export function applyTextDone(
  streamingText: string,
  parts: StreamingAssistantPart[],
  fullText: string
) {
  if (!fullText
      || streamingText.endsWith(fullText)) {
    return { streamingText, streamingParts: parts };
  }
  return {
    streamingText: streamingText + fullText,
    streamingParts: applyTextDelta(parts, fullText),
  };
}

🐛
Bug 根因（已修复）

旧代码用 fullText.endsWith(streamingText) 判定——这是反的！多轮 Run 中 streamingText（全 Run 累积）远长于单轮 fullText，所以 "短短的单轮文本".endsWith("多轮累积的长文本") 永远 false → 每轮 TextDone 都把 streamingText 覆盖成 最新单轮的 fullText → 前面轮次的输出全部消失。

修复：改成 streamingText.endsWith(fullText)——「累积文本的末尾是否是本轮全文」。

toolPartIndex：另一个潜伏 Bug

非流式路径下，工具事件的 index 字段可能是 undefined。旧代码在 index 匹配失败时回退到 part.index === index——当两者的 index 都是 undefined 时，会错误地匹配到上一轮的工具卡片。
