为什么用 Channel 而不是轮询？

如果前端每秒问一次「有新消息吗」，响应会延迟最多 1 秒，而且浪费 CPU。Channel 是「推送」模式——后端有事件就立刻推给前端，延迟是亚毫秒级的。这就是为什么你能看到助手逐字「流」出来。

Agent 大脑的无限循环

run_loop 是 Hebbian 的心脏。它在一个巨大的 loop {} 里反复执行「调模型 → 跑工具 → 再调模型 → 再跑工具」，直到模型说「好了，完成了」。

🧠
比喻：就像你跟一个工程师结对编程

你说「帮我修这个 bug」，他看了看代码说「让我先读一下这个文件」（Read 工具），读了之后说「我需要改第 42 行」（Edit 工具），改完后说「让我跑一下测试」（Bash 工具）——每一步都是「想 → 做 → 看结果 → 再想」。agent_loop 就是把这个循环自动化的引擎。

Turn、Step、Run：三层时间结构

agent_loop 内部有三个层级的时间概念，理解它们是读懂整个系统的前提：

🔄

Run

一次「用户消息 → 全部完成」的完整过程。一个 Run 可能包含多个 Turn。RunFinished 事件标志 Run 结束。

🔁

Turn

一次「问模型 → 执行工具 → 出结果」的循环。TurnFinished 事件标志 Turn 结束。如果模型调了工具，当前 Turn 还没结束——下一轮模型调用仍在同一 Turn 内。

👣

Step

最小的粒度。ModelStep = 一次模型调用。ToolStep = 一批工具并发执行。StepStarted / StepFinished 是调试用的边界事件。

举个具体例子：你说「帮我修个 bug」，模型回复「我先用 Read 读一下 main.rs」，然后调了 Read 工具。这就是 一个 Turn——包含一个 ModelStep（调模型）和一个 ToolStep（执行 Read）。如果模型读完又说「再用 Bash 跑测试」，那就是 同一个 Run 里的第二个 Turn。

agent_loop 发送模型请求时有两条路径：

PLAIN ENGLISH

走流式路径的条件：用户开了 stream 开关，并且...

要么本轮没有工具调用（纯文本回复），

要么当前模型提供商支持「流式工具调用」

🌊

Stream（流式路径）

模型一边生成一边推事件：TextDelta 逐段到达、ToolCallDelta 逐字段填充。前端能看到文字「长出来」的过程。

OpenAI 的 GPT-4 支持流式工具调用。Anthropic 的 Claude 不支持——带工具时必须走 complete 路径。

📦

Complete（非流式路径）

模型一次性返回完整结果。后端收到后 emit TextDelta（全文）和 ToolCallStarted（每个工具一次性到达）。前端仍然按事件处理，但不是「逐字生长」而是「一次出现」。

⚠️
这是理解 Bug 的关键

Anthropic + 工具 = 走 complete 路径。complete 路径下，每轮 Turn 的文本通过 一个 TextDelta（整段）emit，然后每轮 TurnFinished。多轮 Turn 会 emit 多个 TextDelta，每个都是那一轮的完整文本。前端把它们拼接起来——但如果拼接逻辑出错，前面轮次的输出就「消失」了。

事件高速公路

agent_loop 产生的每个事件——TextDelta、ToolCallStarted、TurnFinished——都要经过三层翻译才能到达前端 UI。

想象你在北京寄一封信到上海。信的内容经过三个中转站：你写好信（agent_loop emit）→ 邮局分拣贴标签（chat.rs 翻译）→ 货车运到上海（Tauri Channel）→ 收件人拆开读（前端 useStore）。每一层都可能「翻译」或「过滤」信的内容。

第一层：EventPayload —— agent_loop 说出的「原子话」

agent_loop 里 emit 的不是字符串，而是结构化的 EventPayload 枚举。这是整个系统的「统一语言」。

CODE — crates/protocol/src/event.rs 

pub enum EventPayload {
    // 模型流
    TextDelta { text: String },
    TextDone { full_text: String },
    Reasoning { text: String },
    // 工具
    ToolCallDelta { index, id, name, arguments_delta },
    ToolCallStarted { index, call_id, name, input },
    ToolCallFinished { index, call_id, result, duration_ms, ... },
    // 生命周期
    TurnFinished { turn_id, turn, stop_reason },
    RunFinished { total_input_tokens, duration_ms, ... },
    // 审批
    PermissionRequested { request_id, kind, summary, ... },
    // ... 还有 20+ 种事件
}
PLAIN ENGLISH

EventPayload 是枚举——每种事件是互斥的 variant

TextDelta：模型的文字正在流式到达——「逐字」的那个字

TextDone：完整文本——比如非流式路径下一次性给全文

Reasoning：模型的思考过程（如果开启了推理显示）

ToolCallDelta：工具调用参数在流式到达——流式路径才有

ToolCallStarted：工具调用参数接收完毕，开始执行

ToolCallFinished：工具执行结束，带结果和耗时

TurnFinished：一轮 Turn 结束——模型说完了，工具也跑完了

RunFinished：整个 Run 结束，带总 token 用量、总耗时

PermissionRequested：agent 想做危险操作，请求用户批准

🔑
这是 LLM Agent 的通用设计模式

所有 LLM Agent 框架（LangChain、CrewAI 等）都有类似的结构化事件流。它们把模型的非结构化输出转成结构化的事件序列，让 UI 层能精确响应每一个状态变化，而不是解析自由文本。

第二层：chat.rs —— 从 EventPayload 到 EngineEvent

agent_loop emit 的是协议层事件（Event），但桌面端有自己的翻译层——chat.rs 的 on_event 方法。它做三件事：

1

累积 partial 文本

TextDelta → self.partial_output.push_str(text)。这个 partial 文本用于：崩溃恢复时落盘、中继时保留残片。

2

累积结构化 parts

TextDelta → parts.append_text(text)；ToolCallStarted → parts 里加一条 tool_call 记录。这些 parts 用于：消息落盘到 session.jsonl。

3

翻译并转发

调用 agent_event_to_engine_event(event) 把协议 Event 转成 EngineEvent，然后 (self.emit)(ev) 推给 Tauri Channel → 前端。

特别重要的细节：chat.rs 还会实时写 partial 文件——在 TextDelta/ToolCallStarted 等事件到达时立刻落盘到 ~/.hebbian/sessions/{sid}/partial/。如果 Hebbian 进程崩溃，下次打开对话时会从 partial 文件恢复未保存的输出。

关键细节：TextDelta 的时机

在非流式路径下，TextDelta 在 ModelResponse::ToolCalls 到达时 emit——先于 ToolCallStarted。TextDone 在 ModelResponse::Done 到达时 emit。所以前端会先收到所有 Turn 的 TextDelta，最后才收到一个 TextDone。如果前端在 TextDone 处理时错误地覆盖了之前的累积文本，前面轮次的输出就会消失。

前端状态机

useStore 里的 applyEventToSlot 是前端最核心的纯函数。它把每一个后端事件「折叠」进 slot 状态，驱动整个 UI 的变化。

🎯
比喻：就像快递分拣中心

后端往传送带上放包裹（事件），每个包裹上贴着标签（event.type）。分拣员（applyEventToSlot）看一眼标签，然后把它放到正确的架子上：TextDelta 放 streamingText 架子，ToolCallStarted 放 streamingParts 架子，TurnFinished 检查要不要冻结当前架子的内容……

SessionStream：每个 Run 的状态槽

每次 sendUserMessage 被调用，前端创建一个新的 SessionStream slot。它包含 Run 进行中的所有实时状态：

📝

streamingText

当前 Run 累积的所有文本。每次 TextDelta 就追加。Run 结束 reload 后，由 session.jsonl 接管。

🧩

streamingParts

结构化的输出段：文本、推理、工具调用卡片（按真实发生顺序穿插）。MessageBubble 直接吃这个结构渲染。

📋

liveTimeline

Run 内的时间线：冻结的 assistant 快照 + 用户插队消息。Run 结束清空，由 session.messages 接管渲染。

📍

assistantInsertPos

游标：当前 streaming 在 liveTimeline 里的插入位置。冻结后游标推进到末尾。

applyEventToSlot：事件分发核心

每个后端事件的 type 决定走哪个分支。这是纯函数——接收旧 slot + 事件，返回新 slot。

CODE — useStore.ts:341 

function applyEventToSlot(
  slot: SessionStream,
  e: EngineEvent
): SessionStream {
  if (e.type === "text_delta") {
    return { ...slot,
      streamingText: slot.streamingText + e.text,
      streamingParts: applyTextDelta(slot.streamingParts, e.text)
    };
  }
  if (e.type === "text_done") {
    const r = applyTextDone(
      slot.streamingText, slot.streamingParts, e.full_text);
    return { ...slot, ...r };
  }
  // ... tool_start, tool_done, turn_finished ...
}

Bug 根因（已修复）

旧代码用 fullText.endsWith(streamingText) 判定——这是反的！多轮 Run 中 streamingText（全 Run 累积）远长于单轮 fullText，所以 "短短的单轮文本".endsWith("多轮累积的长文本") 永远 false → 每轮 TextDone 都把 streamingText 覆盖成 最新单轮的 fullText → 前面轮次的输出全部消失。

修复：改成 streamingText.endsWith(fullText)——「累积文本的末尾是否是本轮全文」。

applyTextDone 中，正确的去重判定是？

时间线魔法

Run 跑到一半时，用户可能插话、后台任务可能完成、系统通知可能到达——如何在保持正确时序的同时，让一切看起来顺序自然？

🪄
比喻：就像现场直播的字幕编辑

主持人正在说话（streaming），字幕实时打出来。导播说「插一条观众提问」（injectOrSend），字幕组需要：① 把当前这句冻结为一个完整的句子卡片；② 插上观众提问；③ 主持人继续回答——新的字幕从空白开始。liveTimeline 就是管理这些「冻结卡片」和「插队消息」的数据结构。

1

前端：injectOrSend

检查当前 slot 是否有 active requestId。有 → 调 api.injectUserMessage，后端把消息写入 PendingInputs + 落盘到 session.jsonl。前端在 liveTimeline 末尾追加 user_injected 条目。

2

后端：drain_pending_inputs

在下一个 Turn 边界（TurnFinished 之前），agent_loop 调用 drain_pending_inputs，把插队消息推进 transcript——模型下一轮请求会看到这些消息。

3

前端：turn_finished freeze

TurnFinished 事件到达时，前端检查 liveTimeline 中是否有非 system_notification 的 user_injected 条目。有 → 冻结当前 streaming 为 assistant_frozen，清空 streaming，下个 Turn 从空开始。

🔍
system_notification 不算「插队」

这是故意的设计。后台任务完成通知（BgTaskFinished）虽然也是通过 injectOrSend 注入的，但它带 meta.type === "system_notification"。turn_finished 检查时显式排除它——所以系统通知不会触发 assistant 冻结。它们由 wakeup 排序逻辑钉到对应 assistant 之后，视觉上自然。

Wakeup 排序：让通知待在「对的」assistant 后面

系统通知的物理落盘位置可能在 assistant 之前（通知是即写即落，assistant 要等 stream 完成才落）。但视觉上应该排在它回应的 tool_call 所属的那个 assistant 后面。

Bug 解剖室

两个已修复的流式渲染 Bug，以及一个仍潜伏的隐患。通过解剖它们，你能学会如何在前端状态机里排查「输出消失」类问题。

🔬
比喻：就像法医解剖

每个 Bug 都有自己的「死因」——一个错误的假设、一个时序的 race、一个方向反了的比较。学会解剖 Bug 比学会写正确代码更难，也更有价值。

Bug A：多轮 Run 中前面轮次的文本消失

现象

长对话中（Anthropic + 工具），assistant 已经输出的内容跑着跑着消失了，Run 结束后 reload 恢复。

死因

方向反了的字符串比较。旧代码：

// ❌ 错误：fullText 是单轮文本，streamingText 是多轮累积
if (fullText.endsWith(streamingText)) { return; }
// Turn 1 后 streamingText = "Turn1内容"
// Turn 2 fullText = "Turn2内容"
// "Turn2内容".endsWith("Turn1内容Turn2内容") → 永远 false!
// → 覆盖: streamingText = "Turn2内容"  ← Turn 1 消失!

修复（streamingParts.ts:66）：

// ✅ 正确：streamingText（累积）的末尾是否已是 fullText（本轮）？
if (!fullText || streamingText.endsWith(fullText)) { return; }
// Turn 1 后 streamingText = "Turn1内容"
// Turn 2 fullText = "Turn2内容"
// "Turn1内容Turn2内容".endsWith("Turn2内容") → false → 追加
// streamingText = "Turn1内容Turn2内容" ✅
💡
排查技巧

这种 Bug 用 console.log 很难发现——文本积累是递增的，肉眼看不出来被覆盖。正确的方式是：在 applyTextDone 里加断点，看每次的 streamingText 长度——如果某次 TextDone 后长度 变短 了，那就是被覆盖了。

Bug B：多轮 Run 中工具卡片塌缩

现象

非流式路径下（Anthropic + 工具），多轮 Turn 的工具卡片数量不对——N 个工具塌成 1 个，互相覆盖。

死因

undefined === undefined 的陷阱。非流式路径的 ToolCallStarted 事件 index 字段是 undefined。旧代码的 toolPartIndex 在按 id 找不到时，回退到按 index 匹配：

// ❌ 旧代码：index 匹配无 guard
parts.findIndex(part => part.index === index)
// Turn 1 tool part: { index: undefined }
// Turn 2 tool_start: { index: undefined, id: "call_2" }
// 按 id 找 "call_2" → not found
// 回退到 part.index===index → undefined===undefined → 找到 Turn 1 的 part!
// → 覆盖！Turn 1 工具卡片变 Turn 2 的

修复（streamingParts.ts:96）：

// ✅ 新代码：index == null 时绝不回退
if (index == null) return -1;  // 找不到就是找不到
return parts.findIndex(part => part.type === "tool_call" && part.index === index);

潜伏隐患：triggerWakeupResume 的 race condition

场景

Run 进行中，后台任务完成 → WakeupScheduler 触发 wakeup-fired 事件 → 前端 triggerWakeupResume 调用 injectUserMessage。但如果此时 Run 刚好结束（race condition），injected 返回 false → 回落走 sendUserMessage → 新建 slot，旧 slot 的 streaming 全部丢失。

// useStore.ts:1581 — triggerWakeupResume 的回落路径
if (isForeground) {
    // ⚠️ 当 injectUserMessage 返回 injected=false 或抛异常时
    // 直接调 sendUserMessage —— 这会创建新 slot，替换旧 slot
    await get().sendUserMessage(wakeupXml, [], meta, { skipOptimisticUser: true });
}

触发条件

需要同时满足：① Run 正在进行中（slot 存在）② 后台任务完成触发 wakeup ③ injectUserMessage 返回 false（通常是因为 Run 刚好在 inject 和 backend 处理之间结束了）。这个窗口极小，但在高频率工具调用中可能被撞到。

最干净修法

sendUserMessage 创建新 slot 前，应该先检查旧 slot 的 streaming 是否非空。如果非空，先把 streaming 冻结到 liveTimeline 再替换——或者直接用 waitForRequestRelease 等待旧 run 彻底结束再发新 run。
