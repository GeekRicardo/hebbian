同一件事，写了三遍

Hebbian 有一个 agent 大脑，四个外壳。大脑里发生的每一件事，都要"翻译"成各个外壳能看懂的话。问题是——这套翻译被写了三遍，三遍还慢慢对不上了。

这门课讲的是一次真实的代码重构：怎么发现"同一件事写了三遍"这个隐患，怎么把它收口成"只写一遍"，以及——怎么证明改完之后什么都没坏。

你不需要会写代码。你只需要理解一个软件工程里反复出现的核心矛盾：重复是怎么悄悄变成 bug 的。理解了它，你就能在指挥 AI 写代码时，提前闻到这种味道。

一个大脑，四个壳

Hebbian 是个 AI agent 框架。它的设计哲学叫"一套核心、多 surface"：真正干活的逻辑只有一份，放在中间叫 agent-core 的地方；外面套四个不同的壳，让不同的人用不同的方式接触它。

🖥️
Desktop（桌面 App）

用 Tauri 做的桌面窗口，普通用户点点点用的图形界面

⌨️
heb CLI（命令行）

给 AI 脚本用的纯文字接口，事件一行一行往外吐，方便程序解析

🌐
hebweb（网页版）

浏览器里打开的版本，和桌面共用同一套界面代码

💬
channel-gateway（渠道网关）

接微信这类聊天软件，让你在微信里直接和 agent 对话

🎯
为什么要分壳？

因为不同的人用法不同：你想点窗口，AI 脚本想读纯文本，远程用户想开网页。但他们要的"agent 能力"是同一个。把能力做一份、壳做多个，就不用维护四套 agent。

麻烦出在"翻译"这一步

大脑内部用的是一种"专业语言"——程序员叫它领域模型，强类型、嵌套深，方便内部逻辑处理。但屏幕、命令行、网页这些壳看不懂这种语言，需要先翻译成它们各自能消费的"大白话"。

这层翻译本身是合理的。问题是——它被分别写了三遍：桌面写了一套，命令行写了一套，网页又写了一套。

🖥️

桌面那套翻译

把内部事件翻成 EngineEvent，丢了 token 用量字段

⌨️

命令行那套翻译

翻成 DaemonEvent，把工具结果截断到 500 字

🌐

网页那套翻译

翻成另一个 EngineEvent，"失败"事件翻成了不同的名字

⚠️
这就是 bug 的温床

三套翻译各写各的，今天有人给桌面加个字段，忘了同步给另外两套——三个壳收到的"同一件事"就长得不一样了。用户在桌面看到的和网页看到的对不上，排查起来还特别难，因为你得同时盯三个地方。

一个古老的工程原则

这种"同一件事写多遍，迟早对不上"的隐患，工程师太熟悉了，专门给它起了个名字叫 DRY 原则——Don't Repeat Yourself，别重复你自己。

核心思想很朴素：同一份逻辑，世界上只应该存在一份权威版本。需要它的地方都去引用那一份，而不是各自抄一份。

💡
为什么这对你（指挥 AI 的人）重要

当你让 AI 加功能时，它经常图省事——"复制一份现成的改改"。短期看很快，长期看你就攒了三份会互相矛盾的副本。学会闻到这种味道，你就能对 AI 说："别复制，抽出来做成共享的一份。"这一句话，就是高级工程师和新手的区别。
