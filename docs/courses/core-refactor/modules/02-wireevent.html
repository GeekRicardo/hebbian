机场的广播室

想象一个国际机场。塔台内部用专业术语沟通——航班号、跑道编号、风速参数，密密麻麻、严格精确。但候机厅里的乘客听不懂这些。中间需要一个广播室，把塔台的专业信息翻译成"CA1234 航班现在 8 号登机口开始登机"这种人人都懂的话。

关键是：这个广播室只有一间。无论信息要送到中文显示屏、英文显示屏，还是手机推送，都先经过这同一间广播室翻译，再分发出去。三块屏幕收到的内容必然一致，因为它们都来自同一次翻译。

💡
这正是 Hebbian 的解法

塔台的专业术语 = agent 内部的领域模型（叫 EventPayload）。广播室翻译出的大白话 = 线协议（叫 WireEvent）。而那"唯一的一间广播室" = 一个叫 to_wire 的函数。

两种语言，一道边界

程序里有两种"语言"，它们的形态天然不同，中间这层翻译是合理的边界，不该硬抹掉：

🧠

EventPayload（对内）

领域模型。嵌套枚举、强类型，方便 Rust 内部逻辑精确处理。给程序自己用。

📡

WireEvent（对外）

线协议 DTO。字段拍平、能被网页的 JavaScript 直接消费。给外面的壳用。

线协议这个词里的"线"，就是数据传输的那根线。WireEvent 就是规定"传出去的数据长什么样"的那份约定。

唯一的翻译函数：to_wire

整个系统里，"内部事件 → 对外 WireEvent"的翻译，只有一个函数负责，叫 to_wire。它住在 protocol 这个所有人都依赖的共享地基里。

CODE · wire.rs 
pub fn to_wire(event: &Event) -> Option<WireEvent> {
  match &event.payload {
    EventPayload::TextDelta { text } =>
      WireEvent::TextDelta { text: text.clone() },
    EventPayload::RunFailed { error } =>
      WireEvent::Error { message: ... },
    // ... 37 种事件，每种一条翻译规则
  }
}
大白话

定义一个公开函数 to_wire，吃进一个内部事件，吐出一个对外的 WireEvent。

match 就是"看看这是哪种事件"，挨个对照。

如果是"模型吐了一段文字"，就翻成对外的"文字增量"。

如果是"这一轮失败了"，就翻成对外的"错误"。

一共 37 种事件，每种都在这里、且只在这里，规定怎么翻。

从此整个系统翻译事件，都来这一个地方——再没有第二份。

🔒
"无损"是关键设计

WireEvent 带全部字段，翻译时不做任何精简。各个壳想怎么省略、怎么截断，是各壳自己渲染时的事，不在这层动手。这样翻译层永远只有"完整版"一种产出，不会因为"桌面想省这个、命令行想省那个"又分叉成多份。
