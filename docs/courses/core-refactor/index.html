同一件事，写了三遍

Hebbian 有一个 agent 大脑，四个外壳。大脑里发生的每一件事，都要"翻译"成各个外壳能看懂的话。问题是——这套翻译被写了三遍，三遍还慢慢对不上了。

这门课讲的是一次真实的代码重构：怎么发现"同一件事写了三遍"这个隐患，怎么把它收口成"只写一遍"，以及——怎么证明改完之后什么都没坏。

你不需要会写代码。你只需要理解一个软件工程里反复出现的核心矛盾：重复是怎么悄悄变成 bug 的。理解了它，你就能在指挥 AI 写代码时，提前闻到这种味道。

一个大脑，四个壳

Hebbian 是个 AI agent 框架。它的设计哲学叫"一套核心、多 surface"：真正干活的逻辑只有一份，放在中间叫 agent-core 的地方；外面套四个不同的壳，让不同的人用不同的方式接触它。

🖥️
Desktop（桌面 App）

用 Tauri 做的桌面窗口，普通用户点点点用的图形界面

⌨️
heb CLI（命令行）

给 AI 脚本用的纯文字接口，事件一行一行往外吐，方便程序解析

🌐
hebweb（网页版）

浏览器里打开的版本，和桌面共用同一套界面代码

💬
channel-gateway（渠道网关）

接微信这类聊天软件，让你在微信里直接和 agent 对话

🎯
为什么要分壳？

因为不同的人用法不同：你想点窗口，AI 脚本想读纯文本，远程用户想开网页。但他们要的"agent 能力"是同一个。把能力做一份、壳做多个，就不用维护四套 agent。

麻烦出在"翻译"这一步

大脑内部用的是一种"专业语言"——程序员叫它领域模型，强类型、嵌套深，方便内部逻辑处理。但屏幕、命令行、网页这些壳看不懂这种语言，需要先翻译成它们各自能消费的"大白话"。

这层翻译本身是合理的。问题是——它被分别写了三遍：桌面写了一套，命令行写了一套，网页又写了一套。

🖥️

桌面那套翻译

把内部事件翻成 EngineEvent，丢了 token 用量字段

⌨️

命令行那套翻译

翻成 DaemonEvent，把工具结果截断到 500 字

🌐

网页那套翻译

翻成另一个 EngineEvent，"失败"事件翻成了不同的名字

⚠️
这就是 bug 的温床

三套翻译各写各的，今天有人给桌面加个字段，忘了同步给另外两套——三个壳收到的"同一件事"就长得不一样了。用户在桌面看到的和网页看到的对不上，排查起来还特别难，因为你得同时盯三个地方。

一个古老的工程原则

这种"同一件事写多遍，迟早对不上"的隐患，工程师太熟悉了，专门给它起了个名字叫 DRY 原则——Don't Repeat Yourself，别重复你自己。

核心思想很朴素：同一份逻辑，世界上只应该存在一份权威版本。需要它的地方都去引用那一份，而不是各自抄一份。

💡
为什么这对你（指挥 AI 的人）重要

当你让 AI 加功能时，它经常图省事——"复制一份现成的改改"。短期看很快，长期看你就攒了三份会互相矛盾的副本。学会闻到这种味道，你就能对 AI 说："别复制，抽出来做成共享的一份。"这一句话，就是高级工程师和新手的区别。

机场的广播室

想象一个国际机场。塔台内部用专业术语沟通——航班号、跑道编号、风速参数，密密麻麻、严格精确。但候机厅里的乘客听不懂这些。中间需要一个广播室，把塔台的专业信息翻译成"CA1234 航班现在 8 号登机口开始登机"这种人人都懂的话。

关键是：这个广播室只有一间。无论信息要送到中文显示屏、英文显示屏，还是手机推送，都先经过这同一间广播室翻译，再分发出去。三块屏幕收到的内容必然一致，因为它们都来自同一次翻译。

💡
这正是 Hebbian 的解法

塔台的专业术语 = agent 内部的领域模型（叫 EventPayload）。广播室翻译出的大白话 = 线协议（叫 WireEvent）。而那"唯一的一间广播室" = 一个叫 to_wire 的函数。

两种语言，一道边界

程序里有两种"语言"，它们的形态天然不同，中间这层翻译是合理的边界，不该硬抹掉：

🧠

EventPayload（对内）

领域模型。嵌套枚举、强类型，方便 Rust 内部逻辑精确处理。给程序自己用。

📡

WireEvent（对外）

线协议 DTO。字段拍平、能被网页的 JavaScript 直接消费。给外面的壳用。

线协议这个词里的"线"，就是数据传输的那根线。WireEvent 就是规定"传出去的数据长什么样"的那份约定。

唯一的翻译函数：to_wire

整个系统里，"内部事件 → 对外 WireEvent"的翻译，只有一个函数负责，叫 to_wire。它住在 protocol 这个所有人都依赖的共享地基里。

CODE · wire.rs 
pub fn to_wire(event: &Event) -> Option<WireEvent> {
  match &event.payload {
    EventPayload::TextDelta { text } =>
      WireEvent::TextDelta { text: text.clone() },
    EventPayload::RunFailed { error } =>
      WireEvent::Error { message: ... },
    // ... 37 种事件，每种一条翻译规则
  }
}
大白话

定义一个公开函数 to_wire，吃进一个内部事件，吐出一个对外的 WireEvent。

match 就是"看看这是哪种事件"，挨个对照。

如果是"模型吐了一段文字"，就翻成对外的"文字增量"。

如果是"这一轮失败了"，就翻成对外的"错误"。

一共 37 种事件，每种都在这里、且只在这里，规定怎么翻。

从此整个系统翻译事件，都来这一个地方——再没有第二份。

🔒
"无损"是关键设计

WireEvent 带全部字段，翻译时不做任何精简。各个壳想怎么省略、怎么截断，是各壳自己渲染时的事，不在这层动手。这样翻译层永远只有"完整版"一种产出，不会因为"桌面想省这个、命令行想省那个"又分叉成多份。

三个壳，三种搬法

收口的目标一样——都改用 to_wire。但三个壳的现状不同，搬过来的"动作"也不同。像三间老房子翻新：有的拆旧墙就行，有的整间推平重盖，有的得小心保留承重结构。

1

2
网页：整个翻译文件删掉

它那套翻译独占一个文件，连同自定义事件类型一起整文件删除，改用 to_wire。

3
命令行：保留类型，只统一字段形态

它的事件类型有"承重作用"不能拆（下个模块详解），但能让字段值复用同一套规范。

🌐
网页

能。那些"多出来的"事件，桌面一直在发，你俩共用同一套前端代码——它早就会处理了。你反而是白捡了功能，向桌面看齐。

📡

桌面：一行替换，删掉一整套

桌面的搬法干净利落。它的"观察者"原本在每个事件出口调旧翻译函数 agent_event_to_engine_event，现在统统换成 to_wire：

CODE · chat.rs（改动示意） 
// 改之前：调桌面自己那套翻译
if let Some(ev) = agent_event_to_engine_event(event) {
  (self.emit)(ev);
}

// 改之后：调全局唯一的 to_wire
if let Some(ev) = protocol::to_wire(event) {
  (self.emit)(ev);
}
大白话

原本：把事件交给桌面自己写的翻译机。

如果翻得出来，就发给前端。

现在：把事件交给全世界唯一的翻译机 to_wire。

逻辑一模一样——只是换了翻译机的牌子。

那套 280 行的旧翻译机，从此可以整个删掉。

🎁
顺手清掉的"僵尸代码"

搬迁过程中还发现两个文件谁都没在用——其中一个甚至依赖另一个早被删掉的文件，根本编译不过的僵尸。重构常常顺带照出这种积灰角落。

广播室 vs. 调度电台

前面说 to_wire 像机场广播室。但命令行这个壳，更像消防队的调度电台——它不只转发广播室的信息，还夹带自己专属的调度指令（"3 号车出动""收到完毕"），而且为了让无线电不卡，长消息会被故意截短。

如果硬把调度电台也换成普通广播室，那些专属调度信号和"截短"的习惯就没了——所有依赖这套电台的设备（自动化脚本）全得重写。这不是统一，是破坏。

🧭
这一节讲的是"分寸"

重构里最难的不是"怎么改"，而是"改到哪儿为止"。命令行就是那条线：它该统一的地方统一，不该动的地方坚决不动。看懂这个判断，比看懂任何代码都值钱。

命令行的事件，是个"超集"

命令行的事件类型叫 DaemonEvent。它不是 WireEvent 的"另一种写法"——它是 WireEvent 的超集：业务事件它都有，外加 WireEvent 根本没有的东西。

Started 命令行专属：守护进程刚启动、报告自己的会话 ID。这是"调度指令"，agent 大脑里压根没有这种事件
result 截断 500 工具输出再长，也只留前 500 字——因为命令行是一行一行往外吐的，超长行会撑爆解析脚本
扁平化字段 把嵌套的权限信息拍平成一层，方便脚本用 jq 这类工具直接挑字段
⚠️
这些不是 bug，是有意设计

命令行的读者是自动化脚本，不是人。脚本要逐行解析 NDJSON，所以截断防爆行、扁平好挑字段，都是为脚本量身定做的。强行换成 WireEvent，等于把这些贴心设计全删了。

关键区分：统一"形态"≠ 替换"类型"

用户当时的要求是"把命令行也统一"。但"统一"有两种截然不同的理解，代价天差地别——这是必须先讲清、再动手的岔路：

✅

统一形态（做了）

保留 DaemonEvent 这个类型，但让它内部那几个字段的写法复用 to_wire 的规范。改动小、不破坏脚本格式。

🚫

替换类型（没做）

把 DaemonEvent 整个换成 WireEvent。破坏 NDJSON 格式、删掉专属信号和截断，所有脚本重写。

读透代码后发现：命令行那几个字段其实是翻译得不一致——它用了一种偷懒写法（直接 dump 内部值），导致同一个"危险等级"，命令行写成 "Critical"，而桌面/网页写成规范的 "critical"。这才是真正该统一的：字段值的形态，不是整个类型。

真正的修法：复用同一套规范

解法很优雅：把 to_wire 内部那几个"枚举转字符串"的小函数公开出来，让命令行直接复用。从此"危险等级怎么写成字符串"，全世界只有一个定义。

CODE · daemon.rs（改动示意） 
// 改之前：命令行偷懒，直接 dump 内部值
risk: format!("{risk:?}"),   // → "Critical"

// 改之后：复用 to_wire 的同一套规范
risk: protocol::risk_str(risk),  // → "critical"
大白话

原本：命令行自己随手把"危险等级"转成文字。

随手转的结果是首字母大写的 "Critical"——和别人不一样。

现在：调用 to_wire 用的同一个 risk_str 函数。

于是三个壳写出来的都是规范的 "critical"，逐字节一致。

📋
改了对外格式，就得改文档

把 "Critical" 改成 "critical" 是对外可见的格式变更——依赖命令行的脚本可能在意。所以这次改动同步更新了命令行的调试文档，把字段的规范取值写清楚。改契约必须连文档一起改，这是纪律。

场景

你在指挥 AI 重构一个系统。AI 提议："把命令行的事件类型也换成统一的 WireEvent，彻底干净。"但你知道命令行有专属的启动信号、有意的输出截断。你该怎么回应？

命令行把工具输出截断到 500 字。这个"截断"逻辑应该放在哪里？

最后一站：改了这么多，怎么证明什么都没坏？

不是"我觉得没坏"，是"我证明没坏"

翻新房子最怕的不是看得见的墙，而是看不见的水管——你以为只是换了个水龙头，结果三楼漏水。代码重构一模一样：删了 600 行、改了四个地方，怎么确定没有哪根"水管"被碰漏？

这一节讲三种"证据"。它们的共同点是：都不靠"我觉得""应该没事""跑一下没报错"——而靠能反复重现的客观事实。这是普通改代码和专业重构的分水岭。

🎯
这是你最该学会向 AI 索取的东西

当 AI 说"我改完了，应该没问题"——这句话毫无价值。你要学会追问："拿出证据。怎么证明旧行为没变？"会逼 AI 给证据的人，交付质量天差地别。

证据一：逐字节对照

这是最硬的一种证据。在写新翻译 to_wire 的那天，就埋了一个测试：拿一批典型事件，同时用新翻译和旧翻译各翻一遍，断言两份结果逐字节相同。

CODE · 对照测试（示意） 
let legacy = agent_event_to_engine_event(&ev);
let wire  = protocol::to_wire(&ev);

assert_eq!(
  legacy_json, wire_json,
  "新旧翻译 JSON 必须逐字节一致"
);
大白话

用旧翻译机翻一遍，得到结果 A。

用新翻译机翻同一个事件，得到结果 B。

assert_eq! 的意思是"断言这俩必须相等"。

把 A 和 B 摆一起比。

只要有一个字节不一样，测试立刻失败、报警。

🪜
它是一架"脚手架"

这个测试的使命就是保证替换那一刻新旧等价。等三个壳都搬完、旧翻译被删掉，它也完成了使命，随旧翻译一起拆掉——脚手架盖完楼就该撤。留着反而会变成"自己跟自己比"的废测试。

证据二：隔离一个"平行宇宙"来对照

改完后跑测试，冒出来 2 个失败。慌不慌？关键问题是：这俩是我改坏的，还是本来就坏的？不查清就甩锅"无关失败"，是不负责任的。

查法很聪明：用 git worktree 在旁边开一个"没有这次改动"的平行版本，在那里跑同一个失败测试。

1

开一个平行版本（不含本次改动）

→
2

在那里跑同一个失败的测试

→
3

它也失败 → 证明本来就坏，与我无关

🔬
这是科学方法：控制变量

"在没有我改动的版本里也失败" = 失败和我的改动无关。另一个失败则是单独跑就过、一起跑才挂——典型的"机器太忙导致的偶发"。两个都查实了，才有资格说"与本次改动无关"。下结论前先排除自己，这是专业的底线。

证据三：真刀真枪跑一遍

测试证明了逻辑，但最有说服力的还是真实世界的输出。用一个真模型（deepseek-flash）起一个命令行会话，让 agent 真的去创建文件、触发审批，然后看吐出来的 NDJSON 里，那个字段到底是不是规范小写。

真实 NDJSON 输出 
{"event":"permission_requested",
 "tool_name":"Bash",
 "risk":"medium"}   ← 规范小写！

{"event":"permission_resolved",
 "decision":"allow_once"}  ← 规范写法！
大白话

agent 要跑一条命令，发出"请求审批"事件。

用的工具是 Bash。

危险等级是 "medium"——小写！正是这次改的。

人批准后，发出"审批已解决"事件。

决定是 "allow_once"——规范的 snake_case，不是偷懒的 Debug 写法。

而且实测还确认了命令行有意的设计没被破坏：工具输出依然被截断、专属的启动信号依然在。该统一的统一了，该保留的也保留了。

三层证据，一个信念

好的重构不是"改得对"，而是"能证明改得对"。每次让 AI 帮你改代码，多问一句"怎么证明旧行为没变"，你的软件就离"production 级可靠"近了一大步。
