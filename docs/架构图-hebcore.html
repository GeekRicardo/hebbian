ZOOM 2 — 一个请求进 hebcore 后怎么走

客户端经 unix-socket 发来的每行 JSON 由 surface_session::transport::handle_connection 按 kind 分派到三条通路（架构 §3 双通路 + §7.8.5 控制 Op）。

通路 A · 同步 APIkind: rpc
1
客户端发 {kind:rpc, req:CoreRequest}
2
dispatch(req, &LocalCoreClient) 大 match
3
转发到 CoreClient 61 方法之一
list_sessions / save_provider / list_skills …
4
回 CoreResponse 强类型 → JSON
通路 B · 对话主链路kind: start_run / subscribe
1
subscribe → 本连接转事件流，订阅 broadcast
2
start_run → RuntimeRegistry.ensure attach runtime
3
input_tx 投文本 → run_turn 跑 agent_loop
4
每个 WireEvent → SessionRuntimeState.emit broadcast
所有 subscribe 的客户端同时收
通路 C · 运行时控制kind: approve / interrupt / …
1
approve / answer → resolve HITL gate（带重试）
2
interrupt → SessionRuntimeState.stop()
3

4
set_run_mode → 即时改 run mode

微观 · 四个关键机制

ZOOM 3 — 让"一套核心多客户端"真正成立的实现细节

每个机制都对应一个曾经的"特例不一致"被根治。

① 事件累积归一§7.8.3
曾经：desktop / web / cli 各写一份"事件流→assistant message"累积器，"同输入→不同落盘"风险。
RunPersister 内唯一 AssistantAccumulator，两份并行累加器： seg 分段落盘（插队 user 插段间）+ full 完整产出（surface 返回值）。三处本地累积器全删。
// observe 同时喂两份累加器 st.seg.on_event(event); // 分段→jsonl st.full.on_event(event); // 全run→返回值
② 单写者 + 多观察者§7.8.5
曾经：跨进程只能共享死文件，§7.6 禁止两客户端碰同一 session。
每个 SessionRuntimeState 一个 broadcast::Sender<WireEvent>。跑 run 的是唯一写者， 所有 surface subscribe() 成观察者，看同一份事件流。 "两进程怎么同步同一对话"这问题自动消失。
pub fn subscribe(&self) -> broadcast::Receiver<WireEvent> { self.event_tx.subscribe() // 多观察者 }
③ dispatch 唯一入口§7.1
曾经：对话主链路在三 surface 各写一遍且不一致（cli 截 result、desktop 丢 token）。
CoreRequest 强类型 enum 覆盖 61 个 CoreClient 方法， dispatch 大 match 唯一处理（对标 codex message_processor）。 全程 serde → in-process 免序列化 / unix-socket / ws 同一套。
pub async fn dispatch(req: CoreRequest, core: &dyn CoreClient) -> CoreResponse { match req { Q::ListSessions => R::from_result(core.list_sessions(), …), …61 个 variant } }
④ connect_or_spawn 单例§7.8.1
曾经无常驻进程。现在：谁先启动谁负责拉起 core，重复拉起必须安全。
任何 surface 启动时 ensure_running：连得上=已有 core； 连不上拉起内嵌二进制。flock 单例锁守 hebcore.lock——第二实例拿不到锁即退， 保证同一数据目录最多一个 hebcore。
fn connect_or_spawn(sock) { if let Ok(s) = UnixStream::connect(sock) { return s } spawn_bundled_hebcore(); // 拉起，单例锁兜底 // 轮询等 sock 就绪 ~5s }

微观 · 一次对话的完整旅程

ZOOM 4 — desktop 发一条消息，字节怎么流

把前面所有层串起来：desktop 用户敲下回车，到 assistant 回复落盘 + 渲染的全链路。

D1
desktop send_message Tauri 命令 → spawn_blocking(run_conversation)
D2
connect_or_spawn 连 hebcore.sock（没起就拉起）
D3
两条连接：subscribe（先建，不漏早期事件）+ start_run（投文本）
C1
hebcore transport::handle_connection 收 start_run → RuntimeRegistry.ensure
C2
input_tx 投文本 → run_turn 构造 Harness + CoreSession，跑 agent_loop
C3
agent_loop 每个事件 → sink → SessionRuntimeState.emit broadcast
P1
RunPersister.observe 同步喂 seg+full 累加器；段边界 flush_segment 落 jsonl
D4
subscribe 连接收回每个 WireEvent → DesktopHebcoreSink
D5
sink 三出口转发：灵动岛 + 微信转发 + 前端 Channel（流式渲染）
H?
同时：另一个 heb / 浏览器若 subscribe 同 session，同一份事件流实时同收
C4
遇审批 → emit PermissionRequested；desktop 弹窗 → approve 经 transport 回流（带时序重试）
P2
run 收尾 RunPersister.finish：补落尾段 + full.build() 写 last_message
D6
run_finished → desktop getSession 从 jsonl 重载，渲染最终态
D desktop 客户端
C hebcore 进程
P RunPersister 落盘
H 其他客户端共享
