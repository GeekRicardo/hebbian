# 设计提案：前后端协同 v2（可靠事件流 + 单一投影 + 闭环记忆）

> **状态：提案，待评审。** 评审通过后按 §11 的清单拆解合入 [架构.md](架构.md) 对应章节，再开始实施。
>
> 本提案针对 2026-07-12 全盘诊断发现的四组结构性缺陷：
> ① 事件流是"尽力而为观察通道"，无 seq / 无回放 / Lagged 静默丢弃，后端自发起的 run 前端整段看不见；
> ② 前端运行态建立在"run 都是我发起的"前提上（slot 只由 sendUserMessage 创建），wakeup/notification 续跑全盘失真，且 `wakeup-fired` / `pendingWakeups` 是从未接线的死代码；
> ③ 同一对话存在多套数据表示（流式 StreamingAssistantPart vs 落盘 Message.parts、liveTimeline vs messages、四条协议翻译路径），靠 run 结束全量 reload 硬对账——这个 reload 同时是长对话卡顿尖峰的来源；
> ④ 记忆系统的漂移门控 / 衰减 / 强化 / 深睡分档是死代码或装饰性实现，注入语义与静态指令矛盾。

---

## 0. 目标与设计原则

1. **后端是唯一真相源，前端是纯投影仪。** 前端不再"乐观造消息 + 事后对账"；一切渲染状态都是后端事件流的确定性投影。谁发起的 run（用户 / wakeup / cron / 队列）对前端完全透明。
2. **事件流升级为 snapshot + log。** 每个 session 的事件带单调 seq，后端保留有界回放缓冲；订阅方可以从任意 seq 续传，缓冲不够时显式收到 resync 指令而不是静默丢失。这推翻架构.md §7.5"事件流不承担 replay"的既定决策——诊断证明只要 run 可以由后端自主发起，同进程内的前端就等价于一个"可能中途加入、可能掉线"的订阅者。
3. **一切进入 transcript 的内容都有事件。** user 消息（无论谁提交）、assistant 段定稿、marker，落盘即广播 `MessageAppended`。前端渲染顺序 = 落盘物理顺序，不再需要任何重排投影。
4. **一份数据形态贯穿实时与历史。** 流式只是 timeline 尾部"未定稿"的条目，定稿靠事件原地替换，不靠磁盘 reload。
5. **幂等优先于精确。** 快照 cursor 允许低估（宁可重放重复），reducer 按 id upsert 幂等消化重复——用简单的不变量换掉复杂的时序协调。
6. **闭环或删除。** 半实现的承诺（importance 只写不读、Auto/Always 同行为、episode "会衰减"）比不实现更糟；本提案里每个字段要么进入闭环，要么删除。

## 1. 可靠事件流：信封、回放缓冲、订阅协议

### 1.1 事件信封 `SessionEnvelope`

`protocol` crate 新增（WireEvent 本体不动，包一层）：

```rust
pub struct SessionEnvelope {
    /// SessionRuntimeState 创建时随机生成。runtime 被 drop / 重建（进程重启、
    /// registry remove 后 ensure）→ epoch 变化 → 订阅方必须 resync。
    pub epoch: u64,
    /// session 内单调递增，从 1 开始，AtomicU64。epoch 内保证连续无洞。
    pub seq: u64,
    /// 本事件所属 run；session 级事件（如 QueueChanged）为 None。
    pub run_id: Option<String>,
    pub ts_ms: i64,
    pub event: WireEvent,
}
```

为什么 epoch 不持久化：持久化 seq 要处理崩溃时"已落缓冲未落盘"的洞，复杂且无收益——epoch 变化直接触发一次快照 resync，语义简单且正确。

### 1.2 回放缓冲（ring buffer）

`SessionRuntimeState` 内：

```rust
struct EventLog {
    epoch: u64,
    next_seq: AtomicU64,
    buffer: Mutex<VecDeque<SessionEnvelope>>,   // 容量 4096（> broadcast 的 1024）
    broadcast: broadcast::Sender<SessionEnvelope>,
}
```

- `emit(event, run_id)`：锁内分配 seq → push buffer（满则 pop_front）→ broadcast send。锁内完成，保证 buffer 与 broadcast 序一致。
- **无订阅者时事件不再丢失**——buffer 里留着，订阅建立时补发。
- 缓冲是内存有界的：`MessageAppended` 携带完整消息体，长回答会占空间，但与前端本就要持有的快照同数量级，4096 条上限可控；必要时对超大事件（>64KB）只在 buffer 里存"胖事件占位 + 从磁盘按 message id 重取"的瘦引用（P2 优化项，先不做）。

### 1.3 订阅协议

同步命令 `subscribe_session_events` 改签名：

```
subscribe_session_events(session_id, after: Option<{epoch, seq}>)
```

后端逻辑（在 buffer 锁内完成注册，无缝隙）：

1. `after.epoch == log.epoch` 且 `buffer` 覆盖 `after.seq+1` → 先补发缺口，再接 live。
2. 否则 → 先发一条控制帧 `ResyncRequired { epoch, last_seq }`，订阅照常建立（live 事件继续来），前端收到后走 §1.5 快照对齐。

订阅任务的 `Lagged(n)` 处理改为**自愈**：从 buffer 按 `last_delivered_seq + 1` 补读，继续投递——因为 buffer 容量 > broadcast 容量，Lagged 时缺口必在 buffer 内；万一不在（极端），发 `ResyncRequired`。当前"warn + 跳过"的路径删除。

控制帧走同一条 Channel，类型上与 SessionEnvelope 平级：

```ts
type SessionFrame =
  | { type: "event"; envelope: SessionEnvelope }
  | { type: "resync_required"; epoch: number; last_seq: number };
```

### 1.4 快照

`getSession` 升级为 `get_session_snapshot`（core-rpc dispatch 新分支，旧命令保留兼容）：

```rust
pub struct SessionSnapshot {
    pub cursor: Option<EventCursor>,     // { epoch, seq }：读盘前采样
    pub messages: Vec<Message>,          // session.jsonl 全量（含 partial sidecar 合并）
    pub run_state: RunStateDto,          // §2
    pub pending_approvals: Vec<...>,     // 未决审批 / 提问（重连后弹窗可恢复）
    pub input_queue: Vec<QueuedInputDto>,
    pub token_stats: TokenStats,
}
```

**cursor 采样在读盘之前**：之后落盘的消息可能同时出现在快照和后续事件里，靠 reducer 幂等（§5.3）消化。这比"持锁读盘保证精确"简单且同样正确。

### 1.5 前端订阅生命周期（打开会话的正确时序）

```
openSession(sid):
  1. subscribe(sid, after: lastCursor[sid])   // 先订阅，事件开始进入缓冲队列
  2. snapshot = get_session_snapshot(sid)
  3. projection = buildFromSnapshot(snapshot)
  4. 应用缓冲中 seq > snapshot.cursor.seq 的事件（epoch 不匹配则丢弃缓冲重来）
  5. 之后 live 事件直接 apply
```

- 订阅按 session 长期存活（现状保留），跨会话切换不退订；`sendUserMessage` 不再 force 重建订阅（删除 F7 竞态窗口）。
- Channel 断开 / 收到 `ResyncRequired` → 自动重订阅 `after: lastCursor`，必要时重拉快照。重连逻辑收敛在 bridge 层一个 `SessionStreamManager`，store 不感知。

### 1.6 事件补齐（与 §3 协议修订联动）

上线 / 新增以下事件（均为 WireEvent additive variant）：

| 事件 | 语义 |
|---|---|
| `RunStarted { run_id, trigger, mode }` | 不再被 to_wire 丢弃；`trigger: "user" \| "wakeup" \| "cron" \| "queue"` |
| `MessageAppended { message: WireMessage }` | **任何**落盘消息：user（含注入的 notification/wakeup XML）、assistant 段定稿、marker。id 即落盘 id |
| `QueueChanged { items }` | 后端 input 队列快照（§4.3） |
| `RunFinished` 补回 4 个 token totals | 前端 / CLI 不再各自重算 |
| `ToolCallFinished` 补 `truncated` | 三 surface 可见截断标记 |
| `ReasoningDuration` 上线 | 刷新前后"思考用时"一致 |

## 2. Run 生命周期：三态状态机

### 2.1 状态定义

`SessionRuntimeState.active_run: AtomicBool` 替换为：

```rust
pub enum RunState {
    Idle,
    Running   { run_id: String, trigger: RunTrigger },
    Suspended { run_id: String, reason: SuspendReason,
                resumes_at_ms: Option<i64>, waiting_task_ids: Vec<String> },
}
```

转移由 run_turn 驱动，**与对应事件的 emit 同锁完成**（状态和事件永不脱节）：

```
Idle ──StartRun──▶ Running ──RunSuspended──▶ Suspended ──RunResumed──▶ Running
                     │                            │
                RunFinished/Failed/Cancelled   手动 abort
                     ▼                            ▼
                   Idle                         Idle
```

关键修正：挂起路径不再 `clear_active`（现状把 Suspended 和 Idle 混为一谈，`lib.rs:795`）。跨进程重启时，`ensure` runtime 从 `run_checkpoint.json` 恢复 Suspended 态——suspended 真相不再散落在磁盘 + scheduler 内存表两处。

### 2.2 run_id 连续性

**resume 复用 checkpoint 里的原 run_id**（`harness::spawn_run` 接受 `Option<RunId>`）。一个逻辑 run 挂起再唤醒仍是同一个 run：`RunSuspended` / `RunResumed` 的 run_id 对得上，Edits worktree、bg watch、observability span 都按同一 id 归属。现状每次 `RunId::new()` 造成的身份断裂消除。

### 2.3 前端镜像

前端删除 `runningSessions` / `slot.requestId 判活` / `streamingMessageId 判流式` / `deriveSuspendedFromReport` 推拉双源，运行态唯一来源 = 快照的 `run_state` + 生命周期事件推导。取消按钮发 `cancel_run(session_id, run_id)`——按 run_id 取消，不再依赖"我这次请求的 requestId"。

## 4. 消息提交：统一入口 + meta 保真 + 队列收归后端

### 4.1 唯一入口 `submit_message`

替换 `send_message` / `inject_user_message` 双入口（旧命令保留为薄壳转调，一个版本后删）：

```
submit_message(session_id, content, attachments, meta: MessageMeta, options)
  → { message_id, delivery: "injected" | "new_run" | "queued" | "resumed" }
```

后端按 `RunState` 决定路径，**先落盘 → emit MessageAppended → 再投递**：

| RunState | 行为 |
|---|---|
| Running | append 落盘 → inject PendingInputs（下次 ModelStep 前 drain）；若已过最后 drain 点 → 转入队列，`delivery: "queued"` |
| Suspended | append 落盘 → 作为唤醒输入走 resume（用户消息也是合法唤醒源，§4.12 已定） |
| Idle | append 落盘 → input_tx 起新 run。**run_turn 不再重复 append_user**（消灭双写点） |

- `PendingMessageMeta`（单变体收窄层）删除，`PendingInputs` 直接携带完整 `MessageMeta`——活 run 注入与 idle 新 run 的 meta 保真度对称，"注入路径 meta 被改写成 `SystemNotification{kind:"other"}`"的缺陷消除。
- `inject_user_message` idle 时静默丢消息的行为消失（统一入口没有"丢"这个分支）。
- 前端不再乐观 append 消息——气泡由 `MessageAppended` 事件产生，id 天然一致，"乐观 id 与落盘 id 不一致"消除。本地回显延迟 = 一次落盘 + 事件往返（同进程 <5ms），无感。

### 4.2 wakeup 闭环

wakeup 保持纯后端行为（`register_wakeup_resume_handler` 方向正确），但 resume handler 改调 `submit_message(meta: SystemNotification{...})`——于是：

```
bg task 完成 / cron 到点
  → WakeupDispatcher → submit_message
      → session.jsonl append（即写即落，现有语义保留）
      → MessageAppended 事件 ── 前端立刻渲染通知气泡
      → RunStarted { trigger: "wakeup" } ── 前端立刻建投影 slot、亮呼吸点
      → TextDelta... ── 正常流式
```

前端删除整套死代码：`listen("wakeup-fired")`、`listen("session-subscription-resynced")`、`triggerWakeupResume`、`pendingWakeups`、`queueWakeupForSession`、`handleSessionSubscriptionResynced`。"后台任务完成"的 toast 改由 `MessageAppended(meta=SystemNotification)` 且 session ≠ 当前会话时触发。

**bg watch 精确摘除**：cron resume 的 `discard_run(run_id)` 改为按 `task_id` 摘除本次唤醒对应的 watch——同 run 内仍在跑的其他后台任务的完成通知不再被误删（修 `wakeup.rs:440-448` 的定时炸弹）。

### 4.3 输入队列收归后端

前端本地 `inputQueues` 删除。队列真相 = 后端 input_tx 队列 + PendingInputs，变化时 emit `QueueChanged { items }`；前端"排队中"面板是它的纯投影，撤回队列项走同步命令。双 drain 竞态及其缓解代码（`useStore.ts:1341` 一带）随之消失。

## 5. 前端投影架构

### 5.1 结构

```
SessionStreamManager (bridge 层)
  订阅/重连/resync/缓冲对齐（§1.5），对 store 暴露有序去重的 SessionEnvelope 流
        │
        ▼
sessionProjections[sid]: SessionProjection   (zustand store)
  { timeline: TimelineItem[], runState, queue, approvals, tokenStats, cursor }
        │  纯函数 apply(projection, envelope) → projection'
        ▼
组件按细粒度 selector 订阅（ChatView 不再无 selector useStore()）
```

删除清单：`sessionStreams` slot 机制、`liveTimeline` + `liveTimelineOrder` 两套 wakeup 重排投影、`filterMessagesDuplicatedInLiveTimeline`、`runningSessions`、`inputQueues`、run 结束 `getSession` reload、`StreamingAssistantPart` 与 `Message.parts` 双模型及三个 normalize 分支。

### 5.2 统一 TimelineItem

```ts
type TimelineItem = {
  id: string;                    // 落盘 message id（streaming 期为临时 id，定稿时替换）
  role: "user" | "assistant" | "marker";
  status: "final" | "streaming";
  parts: Part[];                 // 与落盘 Message.parts 同构：text / reasoning / tool_call
  meta?: MessageMeta;
  version: number;               // 每次内容变更 +1，供 memo/缓存做失效键
};
```

- 流式事件（TextDelta / ToolCallStarted / ...）折叠进 timeline 尾部 `status: "streaming"` 的 item——**折叠产物就是落盘形态**，不再有第二套。
- 工具卡的 `live_output` / `isJudging` 等瞬态放 item 外的 `ephemera[callId]` 挂件层，定稿不受它污染。
- **渲染顺序 = timeline 数组顺序 = 落盘物理顺序**。wakeup 通知天然先于回应它的 assistant（先落盘先广播），两套重排投影没有存在必要。

### 5.3 定稿与幂等

reducer 的两条核心规则：

1. **`MessageAppended` 按 id upsert**：id 已存在（快照与回放重叠、或 streaming item 已持有该 id）→ 原地替换为 final；不存在 → 追加。这一条同时解决：assistant 段定稿（替换尾部 streaming item）、注入消息渲染、快照 cursor 低估造成的重复。
2. **seq 守门**：`envelope.seq <= projection.cursor.seq` 的事件直接丢弃；epoch 不匹配触发 resync。乱序 / 重复在入口一层解决，下游 reducer 不再需要任何去重逻辑。

run 结束不 reload。快照重载只剩两个场景：resync、冷启动。

### 5.4 eventBatcher 保留但修正

rAF 批处理保留（设计正确），修正帧内重排：按 seq 稳定排序后 dispatch，删除"先所有 text、再所有 tool delta"的固定分组——text 与 tool 事件的交错次序不再丢失。

## 6. 渲染性能

1. **虚拟化消息列表**（结构性根因）：引入 `virtua`（轻量、原生支持 reverse/贴底）或 `@tanstack/react-virtual`。要点：动态高度测量、新消息贴底锚定、流式增高不跳动、Cmd-F 命中跳转、图片/折叠展开时的高度重测。`MessageList` 只挂载视口 ±overscan 的气泡。
2. **markdown 内容寻址缓存**：`buildAssistantRenderParts` 进 `useMemo`，`ReactMarkdown` 渲染结果按 `(item.id, item.version)` memo。final item 的 version 不再变化 → 历史消息永不重解析。做完 §5 后"run 结束全量引用失效"已不存在，这里只需保证 streaming 那一条的重解析不外溢。
3. **流式尾部优化**：streaming item 的 markdown 按"已闭合 block 前缀缓存 + 只重解析尾部未闭合 block"拆分；退而求其次先做 30fps 节流（rAF 批处理已有，加 min-interval 即可）。
4. **selector 化**：ChatView 的无 selector `useStore()` 拆为细粒度 select；`Usage`/tokenStats 更新不再新建 `currentSession` 对象。
5. Cmd-F 查找结果对象引用稳定化（memo per message id），避免每键全列表重渲。

预期效果：打开 1000 条历史会话 = 快照 parse + 视口内 ~20 个气泡渲染；run 结束零尖峰；流式期间每帧成本 = 尾部一条消息的增量。

## 7. 记忆系统闭环

### 7.1 语义收敛：双标签，各司其职

现状的根本矛盾：静态指令描述"首条 L0 索引 + ReadMemory 取详情"，实现却是"每轮内联 L1/L2 全文"。收敛为两个互补机制、两个标签、静态指令如实描述：

| 标签 | 时机 | 内容 | 目的 |
|---|---|---|---|
| `<memory-index>` | 仅首条 user message | global + project 全量 L0 清单（`[id] 摘要`） | 给模型全局目录，配合 ReadMemory 自取 |
| `<memory-recall>` | 话题漂移时（Auto）/ 每轮（Always） | 当轮激活的 ≤5 条：L0 + 高置信附 L1 概览；**永不内联 L2 全文** | 自动联想，降低模型自己翻目录的成本 |

- `base_system.md` 静态段改写：分别解释两个标签 + "recall 是提示不是指令，详情仍用 ReadMemory"。
- **漂移门控接线**（把死代码 `topic_drifted` 变活）：Auto 模式缓存上一轮注入集合与 query 特征，同话题连续轮次不重复注入（transcript 里已有），漂移才重新激活。`Always` = 绕过缓存每轮注入。`Off` = 只有首条 index。三个枚举值终于有三种行为。

### 7.2 强化 / 衰减闭环（importance 与 last_active 进入生命周期）

```
召回打分 = 语义激活分 × recency(last_active) × importance
                                    ▲                ▲
   ReadMemory 命中 / recall 注入 ────┘（更新 last_active）
   深睡按引用频次 EMA 调 importance ──┘
```

- **强化**：`ReadMemory(id)` 调用、recall 注入均记一次 touch（写 `last_active` + 命中计数，append 到 `.memory_log.jsonl`，深睡时聚合）。
- **衰减**：`episode` 类记忆的 recency 因子随时间衰减（半衰期 ~30 天）；`semantic`/偏好类不衰减。低 importance + 长期未 touch 的 episode 由深睡 Full 档**归档**（移入 `memory/archive/`，不删除、可恢复、不再参与召回）——"episode 会衰减"的承诺兑现。
- 抽取模型在候选 JSON 里给 importance 初值（有依据的初值好过恒 0.5）。

### 7.3 深睡三档做实

| 档 | 动作 |
|---|---|
| Light | 机械去重合并：对 L0 做字符 3-gram Jaccard（或 SimHash）相似度，≥阈值的条目合并进已有记忆而不是并存 |
| Deep | Light + 增量建边（只算新条目 × 全库，删掉">80 条整体跳过"的悬崖） |
| Full | Deep + 衰减归档 + 升华（同主题多条 episode 合并提炼成一条 semantic） |

写入侧同样加机械去重：`storage::memory::write` 前先做相似度检查，命中则 merge 而非新建——去重不再完全依赖抽取模型自觉复用 key。每 scope 设总量上限（200），超限触发 Full。

### 7.4 中文召回修正

- 分词引入 `jieba-rs` 替代 CJK 相邻 bigram（消灭"忆系"类噪音 token）。
- "具体词"判定改为**基于记忆库语料的 IDF**：在库内文档频率低的 token 才是强锚点。硬编码 `SPECIFIC_TERMS` / `GENERIC_TERMS` 词表降级为可选 boost，不再是唯一门——系统不再过拟合于作者个人项目的黑话。
- `strong_link` 旁路加主题交集约束：高权边可以放大分数，但不能凭一条边把零 query 交集的记忆拖进注入（修"问 X 却蹦出八竿子打不着的旧笔记"）。

### 7.5 可观测

设置页「记忆」加"本轮召回解释"调试视图：seed 命中了什么 token、扩散走了哪条边、为什么注入/为什么没注入。召回问题从"玄学"变成可检查。

## 9. 迁移路径（每阶段独立可验证、可回退）

### P1 后端可靠事件流（additive，不破坏现有前端）
信封 + EventLog + 订阅协议 `after` 参数 + Lagged 自愈 + `RunStarted`/`MessageAppended`/`QueueChanged`/补字段 + RunState 三态 + run_id 连续性。旧前端忽略未知事件/字段，行为不变。
**验证**：heb NDJSON 看 seq 单调无洞；`ScheduleWakeup 15s` 挂起唤醒脚本，NDJSON 里看到 `RunStarted{trigger:wakeup}` + `MessageAppended`；订阅方 `kill -STOP` 模拟 lag，恢复后事件补齐无缺口。

### P2 submit 统一入口 + 队列收归 + meta 保真
**验证**：活 run 注入 / idle 注入 / suspended 注入三条路径，`session.jsonl` 里 meta 逐字段一致；`inject → 立即 kill 前端 → 重启`，消息不丢。

### P3 前端投影重写 + 虚拟化（最大的一块，建议单独分支）
SessionStreamManager、projection reducer、统一 TimelineItem、定稿机制、删除清单全清、虚拟化 + markdown 缓存。
**验证**：阶段 A/B 复现脚本——① wakeup 续跑期间前端实时流式可见（原 bug 主现象）；② 1000 条会话打开 <500ms、run 结束无卡顿尖峰（Performance 面板对比）；③ 刷新前后同一会话渲染逐像素一致（推理用时、工具卡、嵌套 subagent）。

### P4 协议 codegen + CLI 对齐
ts-rs 生成 types.gen.ts + CI 校验；CLI TUI 迁移 WireEvent。

### P5 记忆闭环
7.1 → 7.4 依序，各自带回归测试（漂移缓存命中/失效、衰减归档、去重合并、jieba 分词召回）。

依赖关系：P2 依赖 P1；P3 依赖 P1（P2 可并行）；P4、P5 独立。若想先要体感改善，虚拟化 + markdown 缓存可以从 P3 里拆出提前做（不依赖任何后端改动）。

## 10. 边界与非目标

- **跨进程 live 事件不在本提案范围**：Desktop 与 heb 同时开、互看对方 live 流，仍是 §7.5 既有边界（文件锁单写者 + 快照）。本提案的 seq/resync 机制是未来做跨进程订阅的正确地基，但不顺手做。
- **不引入持久化事件日志**：回放缓冲是内存有界的；跨进程重启的补齐靠快照（session.jsonl 本来就是持久日志）。
- **不动 agent loop 内核**：run/turn/step 派发、HITL、压缩、hooks 均不变；本提案只动"状态如何对外表达与同步"。
